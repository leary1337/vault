# Как внести изменение

## Рабочий процесс

1. Создайте ветку от актуальной основной ветки, например `docs/go-memory-model`.
2. Измените или добавьте Markdown-файл.
3. Если страница публичная, добавьте её ровно один раз в `docs/SUMMARY.md`.
4. Запустите `pwsh scripts/check-docs.ps1`.
5. Откройте pull request и опишите, что изменилось и какие источники проверены.

## Пути и Markdown

- Используйте lowercase English kebab-case: `docs/go/concurrency/memory-model.md`.
- Заголовок страницы может быть русским.
- Используйте обычные относительные Markdown-ссылки. Wiki-links, block IDs и Obsidian-transclusions запрещены.
- Не добавляйте пустые страницы и каталоги; каждый content-каталог получает `README.md` с обзором и тематическим индексом. Порядок чтения выбирает читатель; обязательные маршруты и цепочки обучения не добавляются.
- Не встраивайте изображения с внешнего hosting. Локальный asset должен иметь осмысленный alt text и относительную ссылку.

## Frontmatter

Каждая content page обязана иметь минимальные и честные метаданные:

```yaml
---
title: Модель памяти Go
description: Гарантии синхронизации и happens-before в Go
tags:
  - go
  - concurrency
updated: 2026-09-10
---
```

Не меняйте `updated`, если правка не включала содержательную техническую проверку. Проверяющий script требует `title`, `description`, `tags` и дату `updated` формата `YYYY-MM-DD`.

## Факты и источники

- Для version-sensitive утверждений используйте официальную документацию, спецификации, release notes или исходный код проекта.
- Отделяйте публичные гарантии от деталей текущей реализации.
- Указывайте условия benchmark и не делайте безусловных performance claims.
- Код должен быть минимальным и по возможности компилируемым.
- В конце крупных страниц добавляйте раздел `Источники` с несколькими релевантными первичными ссылками.

## Понятная статья с глубиной Senior

Начните с объяснения, какую проблему решает механизм, и расшифруйте новые термины. Затем покажите его работу на конкретном примере с входными данными и результатом. Для конкурентного сценария укажите порядок действий участников; для расчёта — единицы и предположения. Разберите границы гарантии, типичный отказ и способ обнаружить его. Не заменяйте объяснение списком названий технологий.

Термин поясняйте в том месте, где он нужен читателю. Подписи схем, описание страницы и ответы на вопросы тоже должны быть понятными. Названия API, команд и протоколов сохраняйте; обычные действия объясняйте по-русски. После команды покажите, какой результат искать и что из него можно заключить. При редактировании прочитайте всю статью: новый вводный абзац не исправляет непонятное основное объяснение или старый хвост.

Ориентир для диагностической статьи — [высокая загрузка CPU](docs/production/high-cpu.md): значение показателя, пример расчёта, различимые причины, команды с интерпретацией и проверка исправления. Такой порядок не обязателен для каждой темы: структура должна помогать понять конкретный механизм.

Завершайте тематическую статью минимум двумя вопросами «Проверь себя» и короткими ответами в раскрываемом блоке. Один вопрос проверяет механизм, другой — применение при изменении условий. Схемы Mermaid пишите вручную там, где важны поток данных, порядок событий или границы компонентов. Для заимствованной картинки сохраните источник, лицензию и атрибуцию в `maintenance/`; изображения, созданные генеративной моделью, в эту редакцию не добавляются.

Отличайте выполненный тест от разбора по спецификации. Дату `updated` меняйте после содержательной правки и проверки использованных источников; не объявляйте все фрагменты исполнимыми, если часть содержит сокращения.

## Pull request

Не смешивайте массовые перемещения и несвязанные технические переписывания. В описании PR перечислите проверки, известные ограничения и темы, оставленные в backlog.

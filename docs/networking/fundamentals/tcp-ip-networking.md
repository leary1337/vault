# Как пакет проходит TCP/IP-сеть

Рассмотрим клиент `192.0.2.10/24`, шлюз `192.0.2.1` и сервер `198.51.100.20:443`. Адреса зарезервированы для документации; это учебная топология.


## Выбор следующего узла

Клиент проверяет таблицу маршрутов. Сервер вне локального `/24`, поэтому следующий узел — шлюз. ARP разрешает MAC шлюза, а не удалённого сервера. Ethernet-кадр получает MAC шлюза, IP-пакет — IP сервера. Маршрутизатор снимает канальную оболочку и строит новую для следующего участка.

```mermaid
flowchart LR
 C[Клиент 192.0.2.10] -->|Кадр к MAC шлюза| R[Шлюз 192.0.2.1]
 R -->|Новый кадр, IP назначения прежний| N[Следующая сеть]
 N --> S[Сервер 198.51.100.20]
```

MAC часто имеет заводское значение, но может назначаться программно или рандомизироваться. Он не является неизменной личностью устройства. Не всякая канальная технология использует Ethernet MAC.

## Порты и соединения

Порт — 16-битное число, поле допускает 0–65535. Нулевой порт зарезервирован в реестре; в API `bind(..., port=0)` обычно просит ОС выбрать свободный порт. Клиент может получить `53000`, сервер слушать `443`. Множество соединений с сервером различаются адресами и портами обеих сторон; номер порта не равен PID процесса.

TCP устанавливает соединение и предоставляет упорядоченный поток. UDP сохраняет границы дейтаграмм, но не повторяет потерянные сообщения. Поэтому нельзя определять UDP просто как «более быстрый TCP».

## Диагностический пример

```bash
ip route get 198.51.100.20
ip neigh show
ss -tn
```

На Linux первая команда показывает выбранные интерфейс, адрес источника и ближайший узел, вторая — соседей локального участка, третья — TCP-соединения. Вывод зависит от реальной топологии. Если маршрут выбирает неверный интерфейс, поиск HTTP-багов преждевременен; если маршрут корректен, но поиск ARP остаётся в состоянии INCOMPLETE (ответ ещё не получен), проверьте локальную сеть и шлюз.

В Kubernetes и VPN добавляются виртуальные интерфейсы, туннели и возможный NAT. Проверять нужно сетевую область приложения, а не только сеть машины. IP не является аутентификацией пользователя; авторизацию проверяет приложение.

## Проверь себя

1. Какой MAC нужен клиенту для обращения к серверу в другой подсети?
2. Почему один порт 443 может обслуживать тысячи соединений?

<details>
<summary>Ответы</summary>

1. MAC выбранного ближайшего узла, обычно шлюза; MAC удалённого сервера за маршрутизатором клиент не разрешает.
2. Соединения различаются адресами сторон: локальный и удалённый IP/порт; один слушающий сокет принимает много отдельных соединений.

</details>

# IP: как пакет проходит между сетями

IP переносит отдельные пакеты от источника к назначению. Каждый маршрутизатор выбирает следующий участок пути по своей таблице. Протокол не обещает доставку, порядок и отсутствие повторов: если они нужны, их обеспечивает транспорт или приложение.

## Как выбирается следующий узел

Узел смотрит адрес назначения и выбирает подходящий маршрут. В обычной таблице предпочтение получает самый длинный совпавший префикс — наиболее конкретное правило. Маршрут указывает интерфейс и, если нужно, адрес следующего маршрутизатора.

IPv4 TTL и IPv6 Hop Limit ограничивают число переходов. Каждый маршрутизатор уменьшает значение; когда дальнейшая пересылка невозможна из-за его исчерпания, пакет отбрасывается и обычно возвращается ICMP Time Exceeded. **TTL здесь не секунды и не срок DNS-кэша**: это ограничение переходов, предотвращающее бесконечное движение по петле.

## Что находится в заголовке

IPv4-заголовок содержит адреса, длину, номер транспортного протокола, TTL, сведения о фрагментации и контрольную сумму заголовка. IPv6 имеет фиксированную базовую часть и дополнительные заголовки; поле Next Header связывает их с транспортом. Контрольной суммы базового IPv6-заголовка нет.

## Почему маленький запрос проходит, а большой застревает

MTU — максимальный размер IP-пакета для конкретного участка. В IPv4 маршрутизатор может разделить пакет на фрагменты, если не установлен запрет DF. В IPv6 маршрутизатор так не делает: размер выбирает источник, который при необходимости использует Fragment header.

Источник узнаёт об ограничении пути через механизм Path MTU Discovery, в том числе сообщения ICMP. Если нужные сообщения блокируются, маленькие пакеты проходят, а большие исчезают без полезной обратной связи. Такой сбой называют MTU black hole. Ниже показан пример туннеля с меньшим MTU.

Сетевые ускорения ОС и карты могут объединять или делить данные вне точки захвата. Поэтому большой фрагмент в tcpdump не обязательно означает, что пакет такого размера ушёл в кабель. TCP сам делит поток на части, а приложение поверх UDP должно выбирать размер сообщения или своё разбиение.

## Почему IP-адрес не проверяет отправителя

Адрес источника может быть подделан, особенно для обмена без соединения, или принадлежать NAT/прокси. Проверка маршрута и фильтрация полезны только в своей области действия. Для подтверждения личности нужны ключи, сертификаты, сессии или другой механизм приложения.

## Разбор на примере

Путь содержит Ethernet MTU 1500 и VPN-участок с MTU 1400. Маленький проверочный запрос проходит, а большой ответ зависает: возможно, пакет превышает PMTU и необходимое ICMP-сообщение блокируется. Исправление — проверить захват пакетов, MTU и ICMP, а не увеличивать срок HTTP-запроса.

```bash
ip route get 198.51.100.20
ip link show
tracepath 198.51.100.20
```

Это диагностические команды Linux. В выводе `ip route get` поле `via` показывает ближайший шлюз, `dev` — выбранный интерфейс, `src` — адрес источника. Если шлюз не нужен, `via` может отсутствовать. `ip link show` показывает MTU интерфейсов: локальные 1500 байт не доказывают такой же предел всего пути. `tracepath` пытается определить переходы и допустимый размер пакета по пути (PMTU); фильтрация ответов может оставить часть пути неизвестной. Сопоставьте эти наблюдения с большим зависающим ответом, а не только с успешным маленьким ping.

IP-пакет, TCP-сегмент и кадр в захвате могут отличаться из-за туннелей и ускорений ОС/оборудования. Очень большой пакет в захвате на машине не доказывает, что по проводу прошёл кадр такого размера.

# Сокеты: интерфейс приложения к сети

Сокет — объект ОС для обмена данными. В Unix-подобной системе приложение обращается к нему по файловому дескриптору, числовой ссылке на открытый ресурс. Это не обычный файл на диске: свойства чтения и записи зависят от типа сокета и протокола.

## Как сервер принимает клиента

Сервер создаёт socket, привязывает адрес через bind и начинает слушать через listen. Затем accept возвращает **новый** сокет для конкретного клиента. Слушающий сокет продолжает принимать следующие соединения; данные клиента идут через новый сокет. Клиент устанавливает связь через connect.

Один слушающий порт может обслуживать много соединений: они различаются адресами и портами обеих сторон. Однако очереди ещё не принятых подключений и скорость accept ограничены. В Linux детали очередей SYN и принятых соединений зависят от настройки ядра.

UDP обычно использует sendto/recvfrom. Вызов connect для UDP выбирает удалённого собеседника по умолчанию и влияет на фильтрацию и ошибки; сетевой handshake он не выполняет и надёжный поток не создаёт.

## Что означает готовность чтения

Блокирующее чтение ждёт данных, конца потока или ошибки. Неблокирующее возвращает EAGAIN, когда данные сейчас недоступны; программа ждёт уведомления о готовности и пытается снова. Уведомление не означает получение целого сообщения: прочитаться может часть, а при конкуренции данные уже мог забрать другой читатель.

Частичные чтения и записи нормальны. В TCP границы чтения не совпадают с записями отправителя, поэтому приложение само выделяет сообщения. Буферы сокета конечны. Успешная запись обычно означает приём данных локальной ОС, а не их обработку удалённым сервером.

## Кто освобождает ресурс

shutdown позволяет завершить одно направление обмена; close освобождает дескриптор. TCP-состояние может некоторое время оставаться после close. Закрывайте сокеты и при успехе, и на ошибочных ветках. Флаг close-on-exec предотвращает ненамеренную передачу дескриптора запускаемой программе; где возможно, устанавливайте его атомарно при создании ресурса.

Срок ожидания операции защищает от бесконечно занятого ресурса. Keepalive и проверки приложения решают другие задачи и не заменяют этот срок. При росте числа открытых сокетов смотрите ошибки accept/connect, состояния и время удержания соединений.

Go для поддерживаемых сетевых сокетов использует механизм уведомлений ОС. Ожидающая goroutine обычно не требует отдельного заблокированного потока ОС. [Netpoller Go](../../go/runtime/netpoller.md), [epoll](../../linux/epoll.md), [жизненный цикл](../backend/connection-lifecycle.md).

## Разбор на примере

У слушающего сокета один файловый дескриптор (FD). После 1000 успешных accept появится ещё 1000 дескрипторов соединений; каждый закрывают при завершении и ошибках. Общий лимит включает файлы и каналы pipe, поэтому допустимое число соединений согласуют с остальными ресурсами.

```text
сервер: socket → bind → listen → accept → отдельный сокет клиента
клиент: socket → connect → write/read → close
```

Уведомление о готовности (readiness) означает «операция может продвинуться сейчас», а не «полное сообщение уже пришло». Даже после уведомления ОС `read` может вернуть часть данных, EOF или ошибку. При неблокирующем вводе-выводе EAGAIN означает необходимость дождаться следующей готовности по правилам цикла событий. Границы сообщений TCP выделяет приложение.

Успешный Write не доказывает сохранение результата удалённой стороной. Срок ожидания нужен на самой блокирующей операции: завершение ожидания другой goroutine не остановит её автоматически. Закрытие общего сокета для отмены одного запроса может прервать остальные запросы.

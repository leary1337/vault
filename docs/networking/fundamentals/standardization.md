# Стандарты и RFC

Стандарт позволяет независимым реализациям понимать друг друга. Для backend-разработчика важно знать, где описан контракт и чем нормативное правило отличается от поведения конкретной библиотеки.


## Кто определяет правила

- IETF разрабатывает интернет-протоколы; документы публикуются в серии RFC.
- IEEE определяет, например, Ethernet и семейство Wi-Fi.
- ISO публикует модели и стандарты, включая OSI.
- IANA ведёт реестры назначенных чисел и имён: порты, типы, параметры протоколов.

Не каждый RFC — Internet Standard. Есть Standards Track, Best Current Practice, Informational, Experimental, Historic и разные потоки публикации. RFC не редактируют как обычную wiki-страницу: новые документы могут его обновлять или заменять, а errata уточняют ошибки.

## Как проверить утверждение

Старый материал говорит «TCP определён RFC 793». В карточке RFC 9293 видно, что он заменяет RFC 793 и консолидирует часть обновлений. Для текущего контракта TCP используйте актуальный стандарт, для исторического объяснения допустим старый документ с явной пометкой.

`MUST`, `SHOULD`, `MAY` в нормативном контексте имеют специальные значения. SHOULD допускает обоснованные исключения после понимания последствий; это не то же самое, что MUST. При чтении проверяйте область действия требования: отправитель, получатель, посредник или конкретный режим.

## Пример ошибки применения

HTTP-метод может быть идемпотентным по стандарту, но библиотека не обязана автоматически повторять его при любой ошибке. Стандарт задаёт смысл операции, клиент — правила повтора, приложение — последствия изменения состояния. Эти три слоя проверяют отдельно.

Противопоставлять TCP/IP как «только de facto» формальной стандартизации неверно: у Internet protocol suite есть формальные спецификации RFC и реестры. Популярность технологии не отменяет нормативных документов.

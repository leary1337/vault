# UDP: отдельные сообщения без гарантии доставки

UDP передаёт отдельные сообщения — дейтаграммы. В отличие от TCP их границы сохраняются. При этом сообщение может потеряться, повториться или прийти после более позднего сообщения: порядок, повторы и подтверждение добавляет приложение, если они ему нужны.

## Что получает приложение

Одна отправка формирует одну дейтаграмму. При слишком маленьком буфере чтения приложение может получить только часть её содержимого; оставшаяся часть не превращается в следующее сообщение. Переполнение очереди приёма тоже приводит к потерям. Поэтому успешная отправка не доказывает получение.

Контрольная сумма обнаруживает часть повреждений. В IPv4 нулевая UDP checksum исторически означает отсутствие проверки. В IPv6 она обычно обязательна; исключения определены для специальных сценариев. Проверка целостности не подтверждает личность отправителя.

## Почему большой пакет — риск

Размер IP-пакета ограничен интерфейсами по пути. Это ограничение называется MTU; минимальное ограничение всего пути — PMTU. Большая дейтаграмма может потребовать фрагментации IP или быть отброшена. Если потерялся один необходимый фрагмент, исходное сообщение не восстановится. Размер полезных данных выбирают с учётом IP/UDP-заголовков и дополнительных туннелей, либо делят сообщение на части в прикладном протоколе.

## Что даёт отсутствие начального обмена

UDP не выполняет сетевой handshake перед первой отправкой. Это уменьшает число начальных обменов, но проверка адреса, защита от подделки, повтор потерянного сообщения и ограничение нагрузки никуда не исчезают. Их должен обеспечить протокол выше. Поэтому утверждение «UDP быстрее TCP» без конкретной задачи ничего не объясняет.

DNS часто отправляет небольшие запросы по UDP; при усечённом ответе требуется другой обмен, обычно TCP. В передаче голоса опоздавший фрагмент может быть уже бесполезен, поэтому повторная доставка не всегда нужна. [QUIC](quic.md), напротив, строит надёжные защищённые потоки поверх UDP.

## Ошибки при эксплуатации

Повторяйте запрос с идентификатором операции: ответ мог потеряться после успешного выполнения. Разнесите повторы во времени, чтобы клиенты не отправляли их одновременно. Ограничивайте ответы на неподтверждённый адрес: поддельный адрес отправителя позволяет направить отражённый трафик на жертву, особенно если ответ больше запроса. Состояние NAT и межсетевого экрана может исчезнуть после простоя, хотя приложение продолжает считать собеседника доступным.

## Разбор на примере

Клиент послал запрос с ID `42`, сервер выполнил действие, ответ потерялся. Клиент снова посылает ID `42`. Если это изменение состояния, серверу нужно помнить результат или иметь естественно идемпотентную операцию. Для чтения можно повторить запрос с ограничением попыток, задержкой и общим сроком.

При MTU 1500 байт обычные заголовки IPv4 без дополнительных опций и UDP занимают 20 + 8 байт: остаётся 1472 байта полезных данных для этого пути. Это не универсальный безопасный размер: туннель, IPv6 и более узкий участок меняют бюджет. Потеря одного IP-фрагмента теряет всю дейтаграмму. Поэтому большие сообщения лучше разбивать на уровне протокола с учётом PMTU.

Сокетный `connect` для UDP может закрепить адрес другой стороны и упростить API, но не выполняет начальный сетевой обмен. Успешный `send` означает принятие локальным стеком, не получение другой стороной.

## Проверь себя

1. Что означает успешный UDP send?
2. Почему отсутствие начального обмена не делает UDP всегда быстрее TCP?

<details>
<summary>Ответы</summary>

1. Локальный стек принял сообщение; подтверждения доставки от UDP нет.

2. Нужные надёжность, безопасность и управление перегрузкой приходится реализовывать выше; результат зависит от нагрузки.

</details>

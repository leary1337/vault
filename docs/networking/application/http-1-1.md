# HTTP/1.1: запросы, ответы и границы сообщений

HTTP задаёт смысл запроса: какой ресурс нужен, какое действие требуется и что означает ответ. HTTP/1.1 описывает передачу этих сообщений через текстовые заголовки и тело, обычно по TCP. Общие правила HTTP заданы в RFC 9110, формат HTTP/1.1 — в RFC 9112.

## Как читать сообщение

Запрос содержит метод, адрес ресурса, версию протокола, заголовки и возможное тело. Ответ содержит код состояния, заголовки и возможное тело. Например, `GET /ads/42` запрашивает представление объявления, `200` сообщает об успешном ответе. Ниже показан условный GET с проверкой версии.

Протокол не требует хранить состояние между запросами. Приложение при этом может использовать сессии и базы данных. «Безопасный» метод не предполагает запрошенного изменения состояния; идемпотентный метод при повторении должен иметь тот же предполагаемый эффект, что и при одном выполнении. Это не обещание одинакового кода ответа: повтор DELETE может вернуть другой статус после удаления.

## Как отделяется тело

TCP передаёт сплошной поток байтов. Получатель применяет правила HTTP, чтобы понять, где заканчивается одно сообщение и начинается следующее. Длину могут задавать `Content-Length` или правила `Transfer-Encoding`; для некоторых сообщений тела нет, а в определённых случаях границу задаёт закрытие соединения.

Если посредник и сервер по-разному разбирают противоречивые длины, злоумышленник может заставить один запрос выглядеть как часть другого. Это подмена границ запроса (request smuggling). Нельзя произвольно выбирать один из конфликтующих заголовков: сервер и прокси должны применять согласованные правила и отклонять некорректные сообщения.

## Зачем повторно использовать соединение

HTTP/1.1 по умолчанию допускает несколько последовательных обменов по одному соединению. Обычный клиент ждёт ответ, затем использует соединение снова. Pipelining разрешает отправить несколько запросов заранее, но ответы остаются упорядоченными; на практике это редко используется. Независимого чередования потоков, как в HTTP/2, здесь нет.

Для параллельных запросов клиент держит несколько соединений в пуле — наборе для повторного использования. Пул ограничивают по количеству и времени простоя. Чтобы соединение можно было использовать снова, библиотеке нужно корректно завершить чтение тела; точные правила чтения и закрытия задаёт её API.

## Сроки ожидания и посредники

Сервер ограничивает время и размер чтения заголовков и тела. Клиент задаёт срок всей операции и, где требуется, отдельных сетевых этапов. Если изменение состояния завершилось на сервере, а ответ потерялся, timeout не отменит изменение. Повтор должен учитывать идемпотентность операции.

прокси принимает запрос и пересылает его дальше; следующая связь может использовать другую версию HTTP. Некоторые заголовки относятся только к текущему соединению и не пересылаются как есть. `Host` помогает выбрать сайт на одном сервере. Заголовки адреса исходного клиента нельзя принимать от произвольного отправителя: доверенный прокси должен очищать их перед установкой собственных значений. Кэширование и условные запросы также требуют явных правил версии и срока хранения.

## Разбор на примере

```http
GET /ads/42 HTTP/1.1
Host: api.example.test
If-None-Match: "v7"

```

ETag обозначает версию представления ресурса. Если она всё ещё имеет значение `"v7"`, сервер может ответить `304 Not Modified` без тела представления. Для изменения клиент отправляет `If-Match: "v7"`: если состояние уже `v8`, предусловие не выполнено — `412 Precondition Failed`. Проверка версии и запись должны быть атомарны, например `UPDATE ... WHERE version = 7`; между отдельным чтением и записью версия могла измениться.

`DELETE` идемпотентен по желаемому эффекту, хотя первый вызов может вернуть 204, второй — 404. `POST` не становится безопасным для повтора от имени метода: нужен отдельный контракт ключа идемпотентности. Для PUT также проверьте побочные действия своей реализации: повтор записи не должен непредусмотренно выполнить отдельное списание или отправку.

Если прокси и сервер различно определяют длину сообщения, одна сторона считает байты продолжением тела, другая — новым запросом. Это подмена границ запроса. Обновляйте библиотеки и проверяйте совместимость посредников; не компенсируйте ошибку самодельным разбором неоднозначных сообщений. Заголовок `Connection` и названные в нём поля относятся к текущему соединению.

## Проверь себя

1. Чем If-None-Match при чтении отличается от If-Match при записи?
2. Должен ли повтор DELETE вернуть тот же код состояния?

1. Первое позволяет не передавать неизменённое представление; второе запрещает запись поверх неожиданной версии.

2. Нет. Идемпотентность описывает эффект повторения, а не идентичность ответа.

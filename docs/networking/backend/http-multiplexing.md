# Несколько HTTP-запросов в одном соединении

Мультиплексирование означает, что части нескольких запросов и ответов передаются по одному соединению, а номера потоков позволяют их различать. Оно уменьшает число соединений, но оставляет общие ограничения. Чтобы понять задержку, выясните, на каком уровне запрос ждёт.

## HTTP/1.1: обмены без независимых потоков

Соединение можно использовать повторно, но в обычном обмене следующий запрос ждёт завершения предыдущего. Pipelining позволяет отправить запросы заранее, однако ответы идут в исходном порядке и этот режим редко используется. Для параллелизма клиенты обычно открывают несколько соединений. Это расходует дополнительные сокеты и требует отдельной установки каждого соединения.

## HTTP/2: чередование кадров поверх TCP

HTTP/2 нумерует потоки и чередует их кадры. Большой ответ не обязан быть полностью передан перед ответом другого потока. Но TCP по-прежнему выдаёт все байты в едином порядке. Потерянный TCP-фрагмент задерживает выдачу последующих байтов сразу нескольких потоков. Это транспортная блокировка из-за начала очереди (head-of-line blocking).

Существуют лимиты приёма для каждого потока и соединения в целом. Если приложение не читает тело, свободное окно заканчивается и отправитель ждёт. Несколько соединений могут разделить часть ресурсов и последствий обрыва, хотя лишние соединения тоже имеют стоимость. HTTP/2 не означает обязательное использование ровно одного соединения для всего клиента.

## HTTP/3: независимый порядок внутри QUIC-потоков

В QUIC порядок байтов задаётся отдельно в каждом потоке. Потеря фрагмента A не требует задерживать уже полученные данные B. Однако потоки делят сеть, управление перегрузкой и ресурсы соединения. Сжатие заголовков QPACK также может заставить поток ждать отсутствующую запись общей таблицы.

Ни одна версия HTTP не убирает очередь перед обработчиком, медленный SQL или блокировку общих данных. Если запросы ждут свободного подключения к БД, смена версии транспорта не решит причину.

## Что сравнивать

Сравните время установки, число параллельных запросов, потери пакетов и фактическое повторное использование соединений. Затем выясните, не исчерпаны ли окна приёма или серверный лимит потоков. Для HTTP/3 учитывайте переход на запасной протокол при недоступном UDP.

Каждый участок пути проверяется отдельно: клиент может использовать HTTP/3 до прокси, а прокси — HTTP/1.1 до сервиса. Для внутренних вызовов ограничения размера сообщений, сроки ожидания и контролируемая очередь нередко влияют сильнее, чем номер HTTP-версии.

## Разбор на примере

| Сценарий | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| Медленный ответ A рядом с B | В обычном режиме обмен занимает соединение; для B помогает другая связь | B не обязан ждать завершения A на уровне HTTP | B не обязан ждать завершения A на уровне HTTP |
| Потерян ранний фрагмент | Ждёт это TCP-соединение | Ждут последующие байты всех потоков общего TCP | Ждут потоки с недостающими данными; общий бюджет перегрузки остаётся |
| Медленная БД | Версия транспорта не исправляет | Версия транспорта не исправляет | Версия транспорта не исправляет |

прокси может принять HTTP/3, затем обратиться к сервису через HTTP/1.1. Проверяйте каждый участок. Несколько соединений разделяют часть последствий отказа, но требуют больше установок и CPU. Размер пула выбирайте по времени самых медленных запросов, скорости обработки, согласованным лимитам и возможностям зависимостей.

Два вида блокировки начала очереди (HOL) различаются: прикладной ответ ждёт предыдущий ответ либо транспорт ждёт недостающие ранние байты. В HTTP/2 устранение первого не устраняет второе. Поэтому вопрос «есть ли HOL?» требует уточнить уровень.

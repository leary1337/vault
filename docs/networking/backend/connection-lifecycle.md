# Жизненный цикл соединения

Соединение может обслужить много запросов. Его создание расходует время, открытое соединение занимает ресурсы, а закрытое ещё некоторое время может оставлять состояние в ОС. Чтобы найти утечку или причину задержки, нужно различать эти этапы.

## От адреса до готового соединения

Обмен различается адресами и портами обеих сторон. Клиент обычно узнаёт IP через DNS, устанавливает TCP и, для HTTPS, TLS. У каждого этапа собственные ошибки: имя может не найтись, порт может отклонить соединение, сертификат может не пройти проверку. Один общий timeout не показывает, на каком этапе всё остановилось.

`LISTEN` означает ожидание новых подключений. `SYN-SENT` и `SYN-RECEIVED` относятся к начальному обмену, `ESTABLISHED` — к установленному соединению. Названия полезны при чтении `ss`, но состояние ESTABLISHED не подтверждает, что запрос уже обработан.

## Что происходит при закрытии

Получив FIN, процесс видит конец входного направления. В `CLOSE-WAIT` он ещё не закрыл свою сторону. Если таких соединений постоянно становится больше, проверьте все пути закрытия socket и тела ответа: удалённая сторона уже закончила обмен, а локальное приложение удерживает ресурс.

`FIN-WAIT-1/2`, `CLOSING` и `LAST-ACK` отражают другие этапы отправки и подтверждения завершения. `TIME-WAIT` обычно остаётся у стороны, начавшей закрытие: ОС защищает новое соединение от старых запоздалых пакетов и может повторить последнее подтверждение. Много TIME-WAIT при частом закрытии ожидаемо; сама эта цифра не доказывает утечку.

## Почему могут закончиться локальные порты

Для исходящего соединения ОС выбирает временный локальный порт (ephemeral port). Число допустимых комбинаций адресов и портов конечно; NAT и прокси имеют собственные таблицы. Частое создание коротких соединений к одному адресу может исчерпать этот ресурс раньше процессора.

Сравните ошибки `connect`, число соединений к конкретному назначению и диапазон временных портов. Повторное использование соединений обычно устраняет причину надёжнее, чем случайная правка `tcp_tw_reuse`. Параметры ядра зависят от версии и условий и могут изменить безопасность повторного использования.

## Пул и проверки доступности

Пул хранит готовые соединения для следующих операций. Маленький пул заставляет запросы ждать свободное соединение, слишком большой перегружает зависимость. Разделяйте максимальное число, допустимый простой, общий возраст и срок ожидания выдачи соединения.

HTTP keep-alive означает повторное использование связи. TCP keepalive — периодические сетевые проверки простаивающей стороны. Проверка приложения, например ping в протоколе БД, проверяет ещё один уровень. Ни одна не гарантирует успешность следующей операции: соединение может закрыться сразу после проверки.

Допустимый простой согласуйте с timeout посредника: он мог забыть связь раньше клиента. Максимальный общий возраст — другое ограничение; он включает активное использование. Разносите обновление соединений во времени, чтобы пул не переподключался целиком одновременно. При ошибке повтора учитывайте, мог ли запрос уже выполниться.

В Go используйте долгоживущие `http.Client` и `Transport`, а тело ответа завершайте по правилам библиотеки. Создание клиента на каждый запрос может мешать повторному использованию. [HTTP-клиент](../../go/backend/http-client.md), [исчерпание пула](../../production/connection-pool-exhaustion.md).

## Разбор на примере

Приложение делает 2000 коротких соединений в секунду к одному адресу. Если условно доступно 28000 комбинаций портов, а закрытые соединения удерживаются 60 секунд, оценка давления — `2000 × 60 = 120000`, заметно выше бюджета. Это модель для поиска риска: фактическое повторное использование зависит от ядра ОС, адресов и назначения, время TIME-WAIT не задаётся произвольной константой для всех систем.

```bash
ss -tan state close-wait
ss -tan state time-wait
ss -s
cat /proc/sys/net/ipv4/ip_local_port_range
```

Команды предназначены для Linux. Растущий CLOSE-WAIT вместе с числом файловых дескрипторов говорит: удалённая сторона уже закрыла направление, локальный процесс не освобождает сокет. TIME-WAIT при стабильном числе дескрипторов скорее объясняется частым закрытием. Исправления разные: освобождение ресурса в первом случае, сокращение частого открытия через повторное использование во втором. Поднимать лимит FD без исправления утечки лишь откладывает отказ.

В Go новые Client с nil Transport делят DefaultTransport; именно отдельный Transport создаёт отдельный пул. Не путайте число объектов Client с числом независимых пулов.

1. Как различить CLOSE-WAIT и TIME-WAIT по ответственности?
2. Как оценить риск исчерпания портов?

<summary>Ответы</summary>

1. CLOSE-WAIT ждёт закрытия локальным приложением после FIN удалённой стороны; TIME-WAIT — штатная защита TCP после активного закрытия.

2. Связать частоту новых соединений, длительность удержания, локальные адреса и сочетаниями адресов и портов назначения; проверить фактические счётчики.

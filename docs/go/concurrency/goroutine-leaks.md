# Утечки горутин

Утечка — горутина, работа которой больше не нужна, но которая не может завершиться или продолжает бесполезно выполняться. Даже без расхода CPU она удерживает стек и доступные через ссылки данные.

## Как появляется утечка

Получатель ушёл по таймауту, а отправитель навсегда ждёт передачи результата. Или `range` ждёт канал, который никто не закроет. Другие причины — сеть без срока, таймер или повторный цикл без остановки, неограниченный запуск под перегрузкой.

## Диагностика

```bash
go tool pprof http://service/debug/pprof/goroutine
```

Подтвердите устойчивый рост числа горутин и сравните их профили во времени. Группируйте по месту ожидания и сопоставляйте с нагрузкой, очередью и версией. Один снимок может показывать нормальных постоянных работников.

Go 1.27 добавил профиль `goroutineleak`: он обнаруживает доказуемо навсегда заблокированные горутины на каналах и поддержанных примитивах `sync`. Он не видит всю логически ненужную работу, внешние операции или случаи, где механизм ожидания остаётся достижимым через живое глобальное состояние.

## Отменяемая отправка

Определение функции; нужен `context`:

```go
func publish(ctx context.Context, out chan<- int, value int) error {
	select {
	case out <- value:
		return nil
	case <-ctx.Done():
		return context.Cause(ctx)
	}
}
```

Если получателя нет, функция ждёт лишь до отмены. Обычная отправка без второй ветки могла бы остаться навсегда. Получение входа тоже должно быть отменяемым: защита только отправки не помогает, если код ещё до неё ждёт пустой незакрытый канал.

## Проверка завершения

После отмены дождитесь собственного `done` работника или его группы с защитным сроком. Точное сравнение общего `NumGoroutine` ненадёжно: тестовая инфраструктура тоже запускает работу.

У каждой горутины нужны владелец, условие остановки и предел количества. Ограничивайте очереди; проверяйте остановку фоновых компонентов. Буфер размером один разрешит одну отправку, но не исправит следующий заблокированный результат.

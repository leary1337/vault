# Примитивы синхронизации

Сначала определите данные и условие, которое должно сохраняться целиком. Затем выбирайте защиту. Например, перевод денег меняет два баланса, поэтому защищать каждое число отдельно недостаточно. Типы `sync` нельзя копировать после начала использования; структуру с ними обычно передают указателем.

## `Mutex`

```go
type Counter struct {
	mu sync.Mutex
	n  int64
}

func (c *Counter) Inc() {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.n++
}
```

Блокировка допускает одного участника в защищённый участок. После `Unlock` изменения видны следующему успешному `Lock` того же мьютекса. Защищайте целостное состояние и держите участок коротким. Мьютекс не привязан к горутине, но передача обязанности разблокировки другой горутине усложняет понимание. Неудачный `TryLock` не создаёт синхронизации.

## `RWMutex`

Допускает несколько читателей или одного писателя. Это не гарантированное ускорение: учёт читателей и конкуренция процессорного кеша могут стоить больше короткого обычного Lock. Измеряйте характерную долю чтений и длительность участка.

Нельзя повысить `RLock` до `Lock` или рекурсивно взять запись. Ожидающий писатель блокирует новых читателей, чтобы получить возможность продолжить.

## `WaitGroup`

С Go 1.25:

```go
var wg sync.WaitGroup
wg.Go(taskA)
wg.Go(taskB)
wg.Wait()
```

Функция для `Go` не должна паниковать. WaitGroup только ждёт; для ошибок и отмены есть `errgroup`. В старой форме `Add(1)` делают до запуска горутины, затем `defer Done`. Положительный Add при нулевом счётчике должен быть до Wait.

## `Once`, `OnceValue`, `OnceValues`

`Once.Do` выполняет функцию один раз, остальные ждут. Паника считается выполнением: второй запуск не произойдёт. `OnceValue`/`OnceValues` запоминают результат и повторяют ту же панику вызывающим.

```go
loadConfig := sync.OnceValues(func() (*Config, error) {
	return readConfig()
})
```

Если временную ошибку инициализации нужно повторить, одного `OnceValues` недостаточно: нужна другая машина состояний.

## `Cond`

```go
c.L.Lock()
for !ready {
	c.Wait()
}
c.L.Unlock()
```

Горутина ждёт изменения условия под общей блокировкой. `Wait` атомарно освобождает блокировку и ждёт, перед возвратом берёт её снова. Проверяйте условие в цикле: другой работник мог забрать ресурс раньше разбуженного. Go не возвращает Wait от произвольного ложного пробуждения, но цикл всё равно нужен. Для одноразового события закрытый канал часто проще.

## `sync.Map` и `sync.Pool`

`sync.Map` подходит отдельным сценариям, например запись один раз и много чтений или непересекающиеся ключи. Для составных условий обычная типизированная карта с мьютексом яснее. `Range` не даёт согласованного снимка всех записей.

`sync.Pool` хранит заменяемые временные объекты: среда выполнения может удалить их в любой момент. Это не обязательный кеш и не надёжное хранилище. После Put объект больше не ваш; очистите чувствительные данные перед передачей.

## Копирование мьютекса ломает защиту

```go
type Store struct {
	mu     sync.Mutex
	values map[string]int
}

func (s *Store) Set(key string, value int) {
	s.mu.Lock()
	defer s.mu.Unlock()
	if s.values == nil {
		s.values = make(map[string]int)
	}
	s.values[key] = value
}
```

Нужен `sync`. Указатель-получатель сохраняет один мьютекс для одной карты. Получатель-значение скопировал бы блокировку, оставив карту общей: два вызова взяли бы разные блокировки и соревновались на общих данных.

## Проверь себя

1. Когда RWMutex может быть хуже Mutex?
2. Можно ли хранить в `sync.Pool` единственный необходимый объект?

<details>
<summary>Ответы</summary>

1. При коротких участках, частых записях и высокой цене учёта читателей; нужно измерение.
2. Нет: элементы могут быть удалены.

</details>

# Runtime Go

Среда выполнения (**runtime**) — код, который стандартный набор инструментов Go связывает с вашей программой. Она запускает горутины, распределяет память, собирает мусор и организует ожидание сети. Поэтому простой вызов чтения может приостановить горутину, не занимая ожидающий поток ОС.

## Что гарантировано

Спецификация языка и контракты пакетов задают поведение `go`, каналов, `panic/recover` и правил видимости записей между горутинами. Приложение не должно зависеть от размеров внутренних очередей, порогов распределителя или расположения G, M и P в памяти.

## Как реализовано в Go 1.27

Планировщик распределяет горутины по потокам ОС. Netpoller приостанавливает ожидание сети, используя механизм платформы. Стеки горутин растут по необходимости, а не требуют большого фиксированного пространства заранее. Сборщик Green Tea находит достижимые объекты кучи и освобождает остальные. Распределитель выдаёт память из областей разных размеров и локальных запасов.

Эти механизмы помогают объяснить задержки и расход ресурсов. При обновлении Go их детали нужно перепроверять: они не являются обещаниями языка.

## Пакет `runtime`

`runtime.Version`, `GOOS` и `GOARCH` показывают версию и платформу. `runtime.NumGoroutine` считает текущие горутины, но не определяет утечки. `runtime/metrics` предоставляет показатели работы среды выполнения.

`runtime.GOMAXPROCS(n)` при положительном `n` вручную ограничивает одновременное выполнение Go-кода и отключает автоматические обновления; при `n <= 0` только читает настройку. `runtime.LockOSThread` нужен для API, привязанных к конкретному потоку ОС. Принудительный `runtime.GC` — специализированный инструмент, а не обычная оптимизация запроса.

## Снять контекст диагностики

Фрагмент внутри `main`; нужны `fmt` и `runtime`:

```go
fmt.Println(runtime.Version(), runtime.GOOS, runtime.GOARCH)
fmt.Println("goroutines:", runtime.NumGoroutine())
fmt.Println("Go parallelism:", runtime.GOMAXPROCS(0))
```

Числа зависят от среды. `GOMAXPROCS(0)` читает текущий предел. При расследовании сохраняйте его вместе с версиями зависимостей, нагрузкой и лимитами контейнера: одинаковый код может работать в разных условиях.

Тысяча новых горутин после открытия тысячи потоков передачи может быть нормальной. Если после закрытия они остаются, изучите их стеки и условие завершения. Для вывода об утечке нужно знать ожидаемый жизненный цикл работы.

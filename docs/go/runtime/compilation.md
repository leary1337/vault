# Компиляция и сборка Go

Компилятор проверяет типы и превращает Go-код в машинные инструкции. Команда `go` выбирает файлы и зависимости, а компоновщик объединяет результат с необходимой средой выполнения. Внутренние этапы и оптимизации могут меняться между версиями.

## Пакеты и кеш сборки

**Пакет** — исходные файлы каталога, которые собираются вместе. **Модуль** — набор пакетов с общим `go.mod`. `go build` строит граф зависимостей пакетов и повторно использует готовые результаты из кеша сборки. Ограничения сборки и `GOOS`/`GOARCH` выбирают подходящие файлы.

`go.mod` задаёт требования версий. Выбор по графу выполняется через minimal version selection с учётом `replace`, `exclude` и рабочего пространства. `go.sum` содержит контрольные суммы содержимого модулей и их `go.mod`, а не фиксированный список выбранных версий.

С Go 1.21 строка `go` задаёт минимальную требуемую версию, а `toolchain` предлагает набор инструментов для главного модуля. `GOTOOLCHAIN=auto` разрешает переключение на более новую версию. Версия языка конкретного пакета остаётся отдельной границей: например, она влияет на переменные цикла.

```bash
go build ./cmd/service
GOOS=linux GOARCH=amd64 go build ./cmd/service
go list -deps ./cmd/service
```

Чистый Go обычно легко собрать для другой платформы. С cgo дополнительно нужны подходящий C-компилятор и библиотеки целевой системы.

## Встраивание и размещение значений

Компилятор может встроить тело функции в место вызова, убрать доказанно ненужные проверки границ и выбрать стек или кучу. При этом должны сохраняться наблюдаемое поведение корректной программы и правила модели памяти. Если в исходнике уже есть гонка данных, нужного порядка между действиями там не было изначально.

```bash
go build -gcflags="all=-m=2" ./...
go build -gcflags="all=-S" ./path/to/pkg
```

Диагностика относится к конкретной версии, платформе и контексту вызова. Не делайте внутреннее решение компилятора архитектурным контрактом.

## Компоновка и сведения о сборке

Компоновщик соединяет пакеты и среду выполнения, удаляет часть недостижимого кода и записывает информацию о сборке:

```bash
go version -m ./service
go tool buildid ./service
```

Так можно проверить, из чего получился бинарный файл. `-ldflags=-s -w` уменьшает его размер ценой части отладочной информации. Для воспроизводимой поставки фиксируйте инструменты и зависимости; состав компонентов и подтверждение происхождения публикуйте отдельно.

## PGO

Профиль CPU позволяет компилятору выбирать оптимизации с учётом реальной работы программы через `-pgo` или `default.pgo`. См. [PGO](../performance/pgo.md). Профиль должен представлять рабочую нагрузку, а эффект нужно измерять; семантика языка от этого не меняется.

## Модули, пакеты и internal

Каталог `internal` ограничивает допустимые импорты родительским деревом. Это граница зависимостей, а не защита секрета. `go get` меняет требования модуля; тестовые файлы выбираются отдельно.

```bash
go mod tidy
go mod graph
go list -m all
go mod verify
go vet ./...
go test ./...
```

`tidy` меняет `go.mod` и `go.sum`: проверьте разницу. `verify` проверяет скачанные данные по контрольным суммам, но не безопасность библиотеки. `vet` ищет подозрительные конструкции, включая копирование блокировок; тесты он не заменяет. Достижимые уязвимые символы отдельно проверяет `govulncheck ./...` из `golang.org/x/vuln/cmd/govulncheck`.

В Go 1.27 `go test` включает анализатор `stdversion`: API должны соответствовать объявленной версии `go`. Новый установленный компилятор не позволяет честно объявить совместимость с Go 1.20 и без ограничений сборки пользоваться API 1.25. Подробности зависимостей — в [инструментах Go](../tooling.md).

## Проверь себя

1. Почему `go.sum` не фиксирует выбранные версии зависимостей?
2. Что доказывает успешный `go vet`?

<details>
<summary>Ответы</summary>

1. Он хранит контрольные суммы; выбор выполняется по графу требований.
2. Проверенные анализаторами подозрительные конструкции не найдены. Корректность программы этим не доказана.

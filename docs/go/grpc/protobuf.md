# Контракты Protobuf

Protobuf связывает каждое поле с числовым номером. По этому номеру читатель понимает двоичные данные. После публикации номер нельзя менять или отдавать другому смыслу: старые данные и клиенты ещё используют его.

```proto
message User {
  string id = 1;
  optional string display_name = 2;
  reserved 3, 4;
  reserved "legacy_name";
}
```

При удалении резервируйте номер и имя. Добавленное поле обычно безопасно для двоичного формата, но приложение должно правильно обработать отсутствие или значение по умолчанию. Неизвестные поля сохраняются или игнорируются по правилам реализации; посредник, обязанный передать исходное сообщение, не должен случайно их потерять.

## Отсутствие и ноль

```proto
syntax = "proto3";

message UpdateAd {
  string id = 1;
  optional int64 price_minor = 2;
}
```

`price_minor` — цена в минимальных денежных единицах. Отсутствие означает «не менять», явный ноль — «сделать бесплатным». Обычное скалярное поле без признака присутствия не различает намерения. Используйте `optional`, сообщение или `oneof` под нужный контракт. В Go механизм присутствия зависит от открытого или opaque API.

Нулевое значение enum должно иметь безопасный смысл вроде `UNSPECIFIED`.

## Совместимость шире кодирования

Изменение `int32` на `int64` может сохранить двоичный способ передачи, но старый читатель потеряет слишком большое число. Совместимость включает диапазон, бизнес-смысл и порядок поставки.

ProtoJSON имеет отдельные правила. Переименование поля может сломать JSON-клиента, даже если двоичный номер прежний. Проверяйте оба формата, когда используется gateway или JSON-хранение. Сгенерированный Go-код не редактируют: фиксируйте `protoc` и плагины и проверяйте несовместимые изменения в CI.

# Детектор гонок

Детектор отмечает выполненные обращения к памяти без нужного порядка. Отчёт показывает две конфликтующие строки и места запуска горутин. Он инструментирует доступ и синхронизацию, поэтому требует дополнительных CPU и памяти.

```bash
go test -race ./...
go test -race -count=20 ./path/to/pkg
go run -race ./cmd/service
```

Используйте характерные конкурентные тесты и ограниченную безопасную среду для нагрузки. Отсутствие отчёта относится лишь к выполненным путям. Подробные правила — в [гонках данных](../concurrency/data-races.md).

## Причинная цепочка отчёта

```text
WARNING: DATA RACE
Write at ... by goroutine 8: cache.go:42
Previous read at ... by goroutine 7: cache.go:19
Goroutine 8 created at: handler.go:55
```

Фрагменты иллюстративны. Определите, один ли объект используется, какие блокировки должны защищать обе стороны и когда изменилось владение. Если писатель берёт mutex, а читатель читает без него, гонка остаётся. Sleep меняет вероятность, но не исправляет порядок.

Детектор не ищет все дедлоки, ошибки повторных команд и конфликты независимых SQL-транзакций. У него конкретная задача — конфликтующие обращения к памяти. Исправление должно задать общий протокол, а не подавить временной симптом.

1. Достаточно ли блокировки только писателя?
2. Доказывает ли `-race` отсутствие дедлока?

<details>
<summary>Ответы</summary>

1. Нет: обычный читатель того же изменяемого состояния тоже должен участвовать в защите.
2. Нет: это другой класс ошибок.

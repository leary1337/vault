# Пакеты, модули и инструменты Go

**Пакет** — исходники каталога, которые компилируются вместе. **Модуль** — пакеты с общим `go.mod`. **Toolchain** — конкретные компилятор, стандартная библиотека и команда `go`. Воспроизводимая сборка требует согласованных исходников, зависимостей и инструментов.

## go.mod и go.sum

```gomod
module example.org/ads

go 1.27

require golang.org/x/sync v0.19.0
```

Это учебное требование версии, а не название последней доступной. Строка `go` задаёт минимально нужный Go и влияет на семантику пакетов. Patch инструментов закрепляют отдельно.

`require` задаёт нижнюю границу. Minimal version selection (**MVS**) выбирает наибольшую требуемую версию каждого пути из графа, а не последнюю в интернете. Если A требует v1.2, а B — v1.4, будет v1.4. `go.sum` хранит контрольные суммы содержимого и файлов `go.mod`, а не список окончательно выбранных версий.

```bash
go mod tidy
go list -m all
go mod graph
go mod why -m golang.org/x/sync
go mod verify
```

`tidy` обновляет требования и суммы по импортам и тестам: проверьте diff. `list -m all` показывает выбранные версии, `why` объясняет зависимость, `verify` проверяет локальный кеш по суммам. Это не проверка безопасности библиотеки.

## Toolchain и граница совместимости

С Go 1.21 `GOTOOLCHAIN=auto` может скачать подходящую версию инструментов. `toolchain` в главном модуле предлагает её для работы с ним, но не меняет произвольно версию языка зависимостей.

```bash
go version
go env GOTOOLCHAIN GOWORK GOOS GOARCH CGO_ENABLED
go list -m all
go version -m ./service
```

Информация бинарного файла помогает узнать реальную сборку. При `go 1.24` установленный Go 1.27 не разрешает обещать поддержку 1.24 и безусловно пользоваться API 1.25. Нужны ограничения сборки и испытание минимальной версии; анализатор `stdversion` помогает найти слишком новые API.

## replace, workspace и vendor

`replace example.org/lib => ../lib` может работать локально, но каталога не будет в CI. Replace главного модуля влияет на граф; replace зависимости не управляет вашим приложением. `go.work` тоже может скрыть неверные требования: проверяйте самостоятельный модуль с `GOWORK=off`.

`go mod vendor` сохраняет выбранные исходники зависимостей и `vendor/modules.txt`. Обновляйте их вместе с `go.mod`; vendor не отменяет лицензии, проверку инструментов и уязвимостей. `-mod=readonly` запрещает менять требования при сборке, а `-mod=vendor` использует сохранённые исходники. Режим выбирайте явно под проект.

## Приватные зависимости

`GOPROXY` выбирает источник скачивания, `GOSUMDB` — службу контрольных сумм. `GOPRIVATE` помечает пути приватных модулей и задаёт настройки обхода публичных служб через GONOPROXY/GONOSUMDB. Это не учётные данные: доступ к Git или прокси настраивается отдельно.

```bash
go env -w GOPRIVATE=git.example.org/team/*
```

Команда постоянно меняет пользовательскую конфигурацию Go; применяйте при нужной политике. В CI удобнее переменные конкретного запуска. Не отключайте проверку сумм глобально ради одного приватного модуля и не записывайте токены в URL, исходники или логи сборки.

## Build tags и CGO

```go
//go:build linux && !cgo

package platform

func Backend() string { return "linux without cgo" }
```

Ограничение выбирает файл до компиляции. Имя `backend_linux.go` также задаёт платформу; для другой нужен альтернативный файл, иначе API исчезнет. Ограничения находятся перед `package` с пустой строкой.

CGO связывает Go с C. Для чистого Go часто достаточно `GOOS=linux GOARCH=arm64`; для C нужны соответствующий компилятор, системные файлы и библиотеки. Динамическую libc нельзя автоматически перенести в scratch. Сборка под платформу не заменяет запуск на ней.

## Разные проверки

```bash
go vet ./...
go test ./...
go test -race ./...
govulncheck ./...
```

`vet` ищет подозрительные конструкции, тесты — нарушение поведения, `-race` — выполненные конфликтующие обращения. `govulncheck` из `golang.org/x/vuln/cmd/govulncheck` сопоставляет зависимости и достижимые вызовы с базой уязвимостей. Учитывайте её версию, условия и доступное исправление. Режим гонок требует поддержанной платформы и обычно cgo/C-инструментов.

Ни одна команда не доказывает безопасность всего продукта. Подробнее — [компиляция](runtime/compilation.md) и [образ Go-сервиса](../containers/docker/production-go-image.md).

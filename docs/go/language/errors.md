# Ошибки в Go

Ошибка — значение, которое возвращают тому, кто может решить, что делать дальше: показать ответ, безопасно повторить действие или остановить работу. Тип `error` — интерфейс с методом `Error() string`.

## Создание и wrapping

```go
var ErrNotFound = errors.New("not found")

func load(id string) error {
	err := query(id)
	if err != nil {
		return fmt.Errorf("load user %q: %w", id, err)
	}
	return nil
}
```

Оборачивание добавляет объяснение операции. `%w` сохраняет исходную причину для `errors.Is` и `errors.As`; `%v` оставляет только текст. Поэтому текст сообщения не подходит для определения категории ошибки: он может измениться без изменения причины.

## Sentinel и typed errors

Заранее объявленная ошибка, например `ErrNotFound`, удобна для стабильной категории. Проверяйте её через `errors.Is`. Собственный тип ошибки нужен, если вызывающему нужны структурированные данные:

```go
type ValidationError struct {
	Field  string
	Reason string
}

func (e *ValidationError) Error() string {
	return e.Field + ": " + e.Reason
}
```

Обработка уже полученной переменной `err`:

```go
var validation *ValidationError
if errors.As(err, &validation) {
	// use validation.Field
}
```

`errors.As` находит подходящий тип внутри обёрток. Обе функции обходят причины через `Unwrap`; тип также может задать методы `Is` и `As`. Делайте такое соответствие частью понятного публичного контракта, а не скрытой эвристикой.

## Несколько причин

```go
return errors.Join(closeDBErr, flushErr)
```

`errors.Join` объединяет несколько ошибок в дерево причин. Это полезно, когда независимо не удалось завершить несколько операций освобождения ресурсов. Решение, какая ошибка важнее для ответа или повторной попытки, всё равно принимает вызывающий код.

## Error boundaries

Код обращения к БД добавляет название операции и сохраняет причину. Сервисный слой переводит её в понятный приложению исход: объект отсутствует, состояние конфликтует, зависимость недоступна. HTTP- или gRPC-обработчик переводит этот исход в код ответа и скрывает внутренние детали.

Так `ErrOrderClosed` остаётся ошибкой предметной области, а не числом `409`. Одну ошибку обычно записывают в лог один раз там, где известны идентификатор запроса и итог работы. Запись на каждом слое создаёт дубли и завышает число отказов. Не отдавайте клиенту текст драйвера БД: он может раскрыть схему, адрес или секрет.

## Retryable и permanent

Таймаут означает, что вызывающий не получил результат вовремя. Он не доказывает, что запись не состоялась. Поэтому перед повтором нужны защита от повторного эффекта, общий срок и число попыток, увеличение паузы со случайным разбросом, а иногда — учёт `Retry-After`. Решение повторять принадлежит операции и вызывающему, а не любому значению `error`.

## Typed nil

```go
func validate() error {
	var err *ValidationError
	return err // non-nil interface: dynamic type присутствует
}
```

Пустой указатель собственного типа внутри интерфейса `error` не делает интерфейс пустым. Если ошибки нет, возвращайте `nil` явно.

## Цепочка ошибок сохраняет смысл

Фрагмент внутри `main`; нужны `errors` и `fmt`:

```go
missing := errors.New("missing")
wrapped := fmt.Errorf("load user: %w", missing)
fmt.Println(wrapped == missing)           // false
fmt.Println(errors.Is(wrapped, missing))  // true
fmt.Println(errors.Join(nil, nil) == nil) // true
```

`==` сравнивает саму обёртку, а `errors.Is` ищет категорию среди причин. `%w` делает внутреннюю ошибку доступной вызывающему и может закрепить её как часть API. Если драйвер не должен становиться частью контракта, переводите его ошибку в устойчивую категорию своего слоя.

## Проверь себя

1. Зачем `errors.Is`, если есть текст ошибки?
2. Можно ли безусловно повторить запись после таймаута?

<details>
<summary>Ответы</summary>

1. Текст изменяем; `Is` проверяет категорию, сохранённую в дереве причин.
2. Нет: запись могла завершиться. Нужна защита от повтора или проверка результата.

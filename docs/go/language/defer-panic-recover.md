# Defer, panic и recover

`defer` планирует действие при выходе из функции: например, закрыть открытый файл. `panic` прерывает обычное выполнение. `recover` позволяет остановить панику на специально выбранной границе, но не исправляет уже испорченные данные.

## `defer`

В `defer f(args)` сама функция и её аргументы вычисляются сразу, а вызов выполняется при выходе. Несколько отложенных вызовов идут в обратном порядке: последний добавленный — первый выполненный. Они выполняются и при обычном `return`, и при раскручивании вызовов из-за паники.

```go
func read(path string) ([]byte, error) {
	f, err := os.Open(path)
	if err != nil {
		return nil, err
	}
	defer f.Close()
	return io.ReadAll(f)
}
```

При записи файла ошибка `Close` может означать неуспешное завершение записи. Если её нельзя потерять, верните или объедините её с основной ошибкой. Именованный результат можно изменить в `defer`, но такая логика должна оставаться явной.

## `panic`

Паника запускает отложенные вызовы текущей горутины и поднимается через вложенные вызовы. Если её никто не восстановил, программа завершается с трассировкой стека. Ожидаемый плохой ввод, недоступная БД или таймаут должны возвращаться как `error`; паника подходит для нарушенного внутреннего условия, при котором безопасное продолжение невозможно.

## `recover`

`recover` действует только при прямом вызове из отложенной функции в той же горутине:

```go
func runSafely(fn func()) (err error) {
	defer func() {
		if value := recover(); value != nil {
			err = fmt.Errorf("handler panic: %v", value)
		}
	}()
	fn()
	return nil
}
```

Граница восстановления может окружать независимый запрос или задание. На ней сохраняют стек через `debug.Stack`, завершают затронутую работу и возвращают безопасный ответ. Если паника оставила общий объект в некорректном состоянии, продолжать пользоваться им нельзя.

## Panic в другой goroutine

```go
go func() {
	defer reportPanic()
	handle(job)
}()
```

Восстановление в родительской горутине не ловит панику дочерней. Если продолжение допустимо, дочерней нужен собственный `defer` с прямым `recover`. При этом запуск должен иметь владельца: кто отменит работу, получит ошибку и дождётся завершения. Для этого используют контекст, канал результата или `errgroup`.

## Порядок видно на коротком примере

Фрагмент внутри `main`; нужен `fmt`:

```go
n := 1
defer fmt.Println("argument", n)
defer func() { fmt.Println("closure", n) }()
n = 2
// при выходе: closure 2, затем argument 1
```

Обычный аргумент первого `defer` зафиксирован при регистрации, а замыкание читает переменную позже. `os.Exit` отложенные вызовы не выполняет. В длинном цикле `defer Close` тоже не закрывает файл в конце итерации: вызовы накопятся до выхода всей функции. Вынесите обработку одной итерации в отдельную функцию.

Не прячьте все ошибки программирования под безусловным `recover`: успех после восстановленной паники нельзя объявлять, если работа не завершилась.

## Проверь себя

1. Почему аргумент и замыкание в `defer` могут напечатать разные значения?
2. Ловит ли `recover` в `main` паники всех горутин?

<details>
<summary>Ответы</summary>

1. Аргумент вычисляется сразу, замыкание читает переменную при отложенном вызове.
2. Нет. Восстановление действует в той же горутине.

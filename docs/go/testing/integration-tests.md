# Интеграционные тесты

Интеграционный тест проверяет настоящее взаимодействие компонентов: протокол, схему БД или файловую систему. Он нужен там, где упрощённая подмена не воспроизводит существенные правила.

## Изоляция

Фиксируйте версию зависимости, применяйте рабочие миграции и создавайте отдельную БД, схему, тему или пространство для запуска. Ждите конкретной готовности с предельным сроком, а не фиксированный Sleep. Освобождайте ресурсы через `t.Cleanup` независимо от результата и не полагайтесь на порядок тестов.

Число параллельных случаев ограничено мощностью CI и зависимости. В отчёте нужны версия, воспроизводимый вход и полезные логи без секретов. Дорогую группу можно отделить тегом сборки или заданием CI, сохраняя её обязательной для затронутой границы.

## Пример файлового взаимодействия

```go
func TestFileRoundTrip(t *testing.T) {
	path := filepath.Join(t.TempDir(), "state.txt")
	if err := os.WriteFile(path, []byte("ready"), 0600); err != nil {
		t.Fatal(err)
	}
	got, err := os.ReadFile(path)
	if err != nil {
		t.Fatal(err)
	}
	if string(got) != "ready" {
		t.Fatalf("got %q", got)
	}
}
```

Нужны `os`, `path/filepath`, `testing`. Тест использует реальный файл, но не доказывает устойчивость при потере питания: ReadFile после WriteFile может читать данные из кеша. Для такого контракта нужны отдельные сценарии fsync/rename и соответствующая ОС и файловая система.

Один успешный сетевой запрос также не доказывает правильность повтора после потерянного ответа. Выбирайте сценарий под конкретный отказ.

# Тесты с БД

Настоящая БД проверяет SQL, ограничения, блокировки и commit, которых нет у карты-подмены. Запускайте фиксированную версию PostgreSQL, применяйте рабочие миграции с нуля и создавайте отдельные данные для теста. Используйте тот же драйвер и путь настройки, что приложение.

## Очистка и транзакции

Откат после каждого теста быстрый, но не проверяет эффекты при commit и не всегда охватывает код с собственными соединениями. Отдельная схема или очистка таблиц дороже, зато позволяет проверить нужное поведение. Очистка выполняется даже после неудачи.

`sql.DB` — пул, а не одно соединение. Ограничивайте его и наблюдайте `DB.Stats`, закрывайте Rows и проверяйте `rows.Err()` после цикла: ошибка может возникнуть уже после успешных строк.

## Сценарий повторной операции

```sql
INSERT INTO orders (idempotency_key, amount_minor) VALUES ('test-42', 100);
INSERT INTO orders (idempotency_key, amount_minor) VALUES ('test-42', 100);
-- вторая запись нарушает UNIQUE: сервис должен вернуть прежний результат
```

Для конкурентного сценария нужны два независимых соединения и барьер, задающий порядок действий. После ошибки транзакция PostgreSQL может требовать rollback; продолжение следующей командой не всегда допустимо.

`SetMaxOpenConns(1)` помогает обнаружить удерживаемое соединение, но открытый первый Rows также заблокирует второй запрос. Это диагностический режим, а не универсальная настройка. Проверяйте отдельно отмену, ограничение уникальности и поведение при фиксации.

## Проверь себя

1. Почему тест с одним rollback может пропустить ограничение commit?
2. Зачем `rows.Err()` после цикла?

<details>
<summary>Ответы</summary>

1. Фиксация не выполнена, а часть проверок происходит именно на ней.
2. Ошибка чтения могла закончить цикл после нескольких успешных строк.

</details>

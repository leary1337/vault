# Подмены зависимостей: stub, fake и mock

Подмена делает тест дешёвым и управляемым. **Stub** возвращает подготовленный ответ. **Fake** выполняет упрощённую логику и хранит состояние, например в памяти. **Mock** проверяет, какие взаимодействия произошли.

```go
type Clock interface{ Now() time.Time }

type fixedClock struct{ now time.Time }

func (c fixedClock) Now() time.Time { return c.now }
```

Предпочитайте проверку результата через небольшой интерфейс возле использующего кода. Проверка каждого внутреннего вызова связывает тест с устройством реализации и мешает изменению структуры.

## Проверка результата и взаимодействия

```go
type UserReader interface {
	Find(context.Context, string) (string, error)
}
type stubReader struct {
	name string
	err  error
}

func (s stubReader) Find(context.Context, string) (string, error) {
	return s.name, s.err
}
```

Нужен `context`. Stub помогает проверить перевод `ErrNotFound` в исход сервиса. Если же правило — «при отказе в правах вообще не обращаться к хранилищу», число вызовов является контрактом: полезен fake со счётчиком или mock.

## Предел подмены

Карта в памяти не воспроизводит SQL, типы, ограничения, транзакции и блокировки PostgreSQL. Документируйте отсутствующие свойства и проверяйте их с настоящей БД.

Сгенерированные mock удобны для больших внешних интерфейсов, но иногда показывают, что интерфейс слишком широк. Если настоящая зависимость дешёвая и детерминированная, создавать абстракцию только ради подмены не обязательно.

1. Чем fake отличается от stub?
2. Когда оправдана проверка числа вызовов?

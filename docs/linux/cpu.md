# CPU: занятость и ожидание процессора

Процессор выполняет инструкции программы. **Занятость** (utilization) показывает, какую часть времени он работал. **Насыщение** (saturation) показывает, ждут ли готовые задачи свободного процессора. Полезно различать эти вопросы: CPU может быть занят полезной работой без растущей очереди.

## Почему среднее может скрыть проблему

На машине с 16 CPU одна последовательная горутина может постоянно занимать один CPU. Средняя занятость будет около 6,25%, но этот участок уже не ускорится без изменения алгоритма или параллелизма. В контейнере с лимитом 1 CPU ограничение может наступить при свободных остальных ядрах.

## Что означают показатели времени

`user` — исполнение кода приложения, `system` — кода ядра, `irq/softirq` — обработка прерываний. `steal` показывает время, которое виртуальной машине не предоставил гипервизор. `iowait` — особый учёт простоя CPU при ожидающем вводе-выводе; это не точный процент времени, которое конкретный процесс ждал диск.

## Диагностика

В командах `$PID` — идентификатор исследуемого процесса:

```bash
mpstat -P ALL 1
pidstat -u -w -p "$PID" 1
top -H -p "$PID"
cat /proc/pressure/cpu
perf stat -p "$PID"
perf record -F 99 -g -p "$PID" -- sleep 30
```

`mpstat` разделяет загрузку по CPU. `pidstat` показывает расход CPU и переключения процесса, `top -H` — его потоки. CPU PSI в `/proc/pressure/cpu` показывает время задержек из-за ожидания ресурса. `perf stat` собирает счётчики, `perf record` — выборочный профиль исполнявшегося кода за 30 секунд.

Сначала уточните, где выросла задержка и что измеряет график: всю машину, контейнер или процесс. Затем проверьте отдельное ядро, очередь готовых задач и паузы из-за квоты. CPU-профиль объясняет исполнявшийся код, но не всё ожидание сети или блокировок. Для Go дополните его трассой выполнения.

`perf` может требовать прав и информации об именах функций; сбор данных сам добавляет нагрузку. Сравнивайте расход на одинаковое число запросов: рост CPU может означать полезный рост нагрузки, повторные запросы, сборку мусора, кодирование данных или пустой активный цикл.

## Квота контейнера

`cpu.max` в cgroup задаёт бюджет процессорного времени за период. Если несколько потоков быстро потратили бюджет, ОС приостанавливает их до следующего периода — это throttling. `cpu.weight` распределяет CPU между конкурирующими группами и не гарантирует абсолютный резерв. В Kubernetes request обычно влияет на размещение и вес, limit — на квоту.

Сравните прирост `nr_throttled` и `throttled_usec` из `cpu.stat` за один интервал с задержкой запросов. Накопленный счётчик без интервала и связь только с низким средним CPU ничего не доказывают.

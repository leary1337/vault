# Слоистая архитектура

Слои разделяют получение запроса, выполнение правил и доступ к данным. Это помогает найти, где происходит изменение поведения, и не копировать правила в каждый обработчик.

## Как это работает

HTTP-слой проверяет форму запроса и переводит ответ в протокол. Сервисный слой выполняет действие продукта: например, проверяет возможность публикации. Слой данных читает и сохраняет состояние. Поток вызовов обычно идёт сверху вниз; запрет циклических зависимостей сохраняет понятные границы.

Не разносите проверку и запись без защиты от одновременного изменения. Сервис может определить правило, а SQL-реализация — обеспечить его условным UPDATE внутри транзакции. Транзакционная граница должна охватывать целое действие, а не случайно совпадать с одним методом слоя.

Более сложная структура оправдана разными причинами изменения. Если сервисный слой только повторяет имя каждого метода хранилища, он добавляет переходы для читателя без отдельной ответственности.

## Разобранный пример

При PATCH цены обработчик разбирает JSON и определяет пользователя. Сервис проверяет право и организует изменение. Правила объявления запрещают отрицательную цену и редактирование закрытого объекта. SQL-код сохраняет с ожидаемой версией. Если проверку прав оставить только в HTTP, будущий обработчик очереди её обойдёт.

Простой CRUD иногда может использовать один тип для API и данных. Когда смыслы различаются, нужны отдельные представления: поле price в API не равно внутренней паре price_minor и currency. Прямое присваивание status=published из JSON не должно обходить модерацию.

## Проверь себя

1. Где должна жить проверка, общая для HTTP и очереди?
2. Когда разделять модели API и хранения?

<details>
<summary>Ответы</summary>

1. В общей операции или её правилах, а не только в одном транспорте.
2. Когда у них различаются смысл, правила изменения или причины развития.

# Репозиторий: контракт доступа к данным

Репозиторий скрывает способ хранения за действиями, нужными приложению. Вместо знания SQL обработчик получает возможность найти объявление или условно изменить его состояние.

## Как это работает

Хороший контракт описывает смысл. PublishIfApproved с ожидаемой версией сообщает больше, чем Save(any): он требует проверить правило и не перетереть конкурентное изменение. Реализация может использовать транзакцию, блокировку или условный запрос, но обязана сохранять договорённость.

Не сводите все ошибки к «не найдено». Конфликт версии, отсутствие строки и недоступность БД требуют разных действий. Аналогично, транзакция нескольких репозиториев должна оставаться одной транзакцией там, где это нужно правилу продукта.

Абстракция не обязана прятать все возможности БД. Для сложной выдачи бывает разумен отдельный запрос чтения с SQL-проекцией. Тестовое хранилище удобно для правил, но не доказывает порядок блокировок, изоляцию и ограничения настоящей базы.

## Разобранный пример

Чтобы не потерять изменение цены, вместо последовательности Get → Save выполняют условный UPDATE с id и expectedVersion, увеличивая версию при успехе. Ноль изменённых строк может означать отсутствие, запрет доступа или конфликт версии. Различайте причины так, чтобы не раскрыть существование чужого объекта.

Если список из пятидесяти карточек вызывает ещё пятьдесят запросов владельцев, абстракция не устранила проблему N+1. Пакетное чтение должно определить порядок результатов, отсутствующие ID и предел размера. Репозиторий, связанный с транзакцией, нельзя использовать после её завершения. При ошибке сериализации заново выполняют всю операцию в новой транзакции.

## Контракт в Go

Это фрагмент интерфейса приложения, а не полная программа. `context` импортируется из стандартной библиотеки; `AdID`, `Ad` и `Money` — типы вашего продукта. `Money` должен задавать сумму и валюту, а не только число с плавающей точкой.

```go
type AdRepository interface {
    Get(ctx context.Context, id AdID) (Ad, error)
    UpdatePrice(ctx context.Context, id AdID, expectedVersion int64, price Money) error
}
```

`Get` возвращает объявление либо ошибку. Контракт уточняет отсутствие, запрет доступа и недоступность хранилища, чтобы вызывающий код не смешивал их. `UpdatePrice` получает ожидаемую версию: реализация изменяет цену только если текущая версия совпала. При конфликте возвращает отдельную ошибку без перезаписи. `ctx` передаёт срок и отмену ввода-вывода; он сам не создаёт транзакцию.

Два клиента прочитали версию 7. Первый меняет цену и создаёт версию 8, второй получает конфликт. Интерфейс выражает требование, но не обеспечивает его сам: реализация делает условный SQL-запрос, а интеграционный тест проверяет два конкурентных изменения.

## Проверь себя

1. Что выражает условие expectedVersion?
2. Почему тестовый репозиторий не заменяет проверку SQL?

<details>
<summary>Ответы</summary>

1. Изменение допустимо лишь для ранее прочитанной версии.
2. Он не воспроизводит автоматически блокировки, изоляцию, ограничения и стоимость запросов.

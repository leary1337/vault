# Шардинг: разделение данных между владельцами

Если одна БД не вмещает объём или нагрузку, данные можно разделить на части — шарды. Каждый объект по правилу размещения попадает к своему владельцу.

## Как это работает

Ключ разделения определяет, какие операции останутся локальными. Если выбрать ID пользователя, его объявления могут находиться вместе, но общий поиск потребует обращения к нескольким частям. Если выбрать ID объявления, данные распределяются ровнее, однако список пользователя становится сложнее.

Перемещение данных между шардами требует протокола: скопировать исходное состояние, передать изменения, переключить владельца и не потерять записи в переходе. Простая смена формулы в клиенте этого не делает. Карта размещения должна иметь версию, а старые клиенты — корректно находить нового владельца.

Разделение увеличивает сложность транзакций, уникальности и диагностики. Один горячий ключ по-прежнему нагружает один шард. Начинайте с измеренного ограничения и правила владения, которое соответствует основным операциям продукта.

## Разобранный пример

Таблица 2 ТБ и двадцать тысяч записей/с не означают, что нужны ровно десять шардов: один клиент способен давать половину работы. Сравните распределение размера, частоты и операций, которые должны быть атомарны.

Перенос начинается со снимка на позиции L. Затем передают изменения после L, прекращают старую запись, догоняют остаток и переключают карту владельцев. Старые клиенты перенаправляются. Без момента прекращения записи старым владельцем появятся две расходящиеся истории.

Глобальная уникальность email при размещении по user_id требует отдельного согласованного владельца email. Проверить все шарды, затем вставить — не атомарно. Обращение к ста шардам для каждого чтения увеличивает нагрузку и зависимость от самых медленных ответов.

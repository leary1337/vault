# Идемпотентность в распределённой обработке

Повторная доставка сообщения нормальна: подтверждение может потеряться после успешной обработки. Получатель должен связать повтор с прежним намерением и не выполнить эффект второй раз.

## Как это работает

Сообщение несёт устойчивый ID, не меняющийся при повторе. Получатель сохраняет этот ID в таблице обработанных событий вместе с изменением своих данных. Если ID уже есть, повтор пропускают или возвращают прежний результат. Два параллельных получателя защищены уникальным ограничением.

Если сначала подтвердить сообщение, а потом сохранить результат, падение теряет работу. Если сначала сохранить результат, а потом подтвердить, после падения возможен повтор — именно его и обезвреживает таблица ID.

Транзакция получателя защищает только его собственное хранилище. Для внешнего эффекта, например письма или платежа, нужна дополнительная договорённость с исполнителем. Срок хранения ID определяет окно защиты, а порядок событий остаётся отдельной задачей.

## Разобранный пример

Клиент создаёт operation_id=pay-17. API сохраняет его, исходящее событие не меняет своего event_id, а обработчик передаёт поставщику pay-17. Если каждый этап выбирает новый ID, местная защита от дублей не доказывает один внешний платёж.

ID трассировки для этого не подходит: новый повтор может иметь новую трассировку, а одна трассировка включать несколько операций. Хеш одинаковых параметров тоже недостаточен: два перевода по сто рублей могут быть разными намерениями.

Если поставщик не поддерживает ID и проверку результата, потеря ответа оставляет неопределённость. Её сохраняют как отдельное состояние и решают сверкой или ручным разбором.

## Проверь себя

1. Почему нельзя выбрать хеш тела единственным ID?
2. Что защищает локальная транзакция получателя?

<details>
<summary>Ответы</summary>

1. Одинаковые параметры могут относиться к разным намерениям.
2. Его собственные данные и запись обработанного ID, но не произвольный внешний эффект.

</details>

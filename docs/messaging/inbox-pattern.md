# Inbox: защита эффекта от повторов

Одно событие может прийти несколько раз: получатель записал результат в базу и упал до сохранения позиции Kafka. **Inbox** хранит идентификаторы применённых событий, чтобы повтор не выполнил бизнес-изменение заново.

## Как связать защиту и эффект

В одной транзакции вставьте идентификатор события в таблицу с уникальным ключом и выполните изменение **только если вставка добавила строку**. Затем сохраните транзакцию БД, потом позицию Kafka. При повторе уникальный ключ не даст добавить тот же идентификатор, а значит, второй эффект не произойдёт.

Отдельная проверка `SELECT` перед `INSERT` оставляет гонку двух исполнителей. Отдельное сохранение маркера до эффекта может потерять обработку; после эффекта — разрешить дубль. Поэтому обе записи обязаны иметь одну границу транзакции.

## Что входит в гарантию

Защищены изменения той же базы. HTTP-вызов не откатывается вместе с SQL: ему нужен собственный ключ идемпотентности или [Outbox: сохранение намерения отправить](transactional-outbox.md). Отправитель сохраняет один `event_id` для повторов того же события, не создаёт новый на каждую попытку.

Таблица растёт. Срок хранения идентификаторов должен покрывать все возможные повторы: задержки Kafka, ручное воспроизведение, очередь ошибок и восстановление старой копии. Удалённый слишком рано маркер снова разрешает эффект.

Иногда естественный уникальный бизнес-ключ или номер версии сущности заменяет отдельную таблицу. Но простое сложение счётчика не безопасно при повторе; максимальная версия или добавление в множество имеют другие свойства.

## SQL без гонки SELECT → INSERT

```sql
CREATE TABLE consumer_inbox(
    consumer_name text NOT NULL,event_id text NOT NULL,
    received_at timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY(consumer_name,event_id)
);
CREATE TABLE inbox_totals(id integer PRIMARY KEY,total bigint NOT NULL);
INSERT INTO inbox_totals VALUES (1,0);
BEGIN;
WITH accepted AS (
    INSERT INTO consumer_inbox(consumer_name,event_id)
    VALUES ('billing','e-42') ON CONFLICT DO NOTHING RETURNING event_id
)
UPDATE inbox_totals SET total=total+100
WHERE id=1 AND EXISTS(SELECT 1 FROM accepted)
RETURNING total;
-- первый запуск: 100; повтор: 0 обновлённых строк, total остаётся 100
COMMIT;
```

Обработка от BEGIN до COMMIT выполняется как одна транзакция. Для повтора запустите только этот участок: создание таблиц и начальная строка нужны один раз. Первое событие вставляет маркер и увеличивает итог до 100; повторная вставка не возвращает строку, поэтому условие обновления ложно. В реальном приложении отсутствие ожидаемой бизнес-строки должно приводить к откату: иначе маркер сохранится без эффекта. Проверяйте число изменённых строк в явной транзакции.

```mermaid
flowchart LR
    Event[Событие e-42] --> Tx[Транзакция БД]
    Tx --> Marker[Уникальный маркер события]
    Marker --> Change[Бизнес-изменение]
    Change --> Commit[COMMIT БД]
    Commit --> Offset[Сохранение следующей позиции]
```

Падение между сохранением БД и позиции Kafka повторит событие, но маркер предотвратит второй эффект. Его преждевременное удаление снова разрешит обработку. HTTP-вызов внутри SQL-транзакции не становится её частью: передайте внешнему сервису ключ идемпотентности или сохраните намерение через outbox.

1. **Почему маркер и изменение сохраняют вместе?**

   <details>
   <summary>Ответ</summary>

   Маркер раньше эффекта может потерять обработку; после эффекта — разрешить повтор. Одна транзакция связывает оба результата.

   </details>

2. **Как выбрать срок хранения inbox?**

   <details>
   <summary>Ответ</summary>

   Он покрывает задержки доставки, ручное повторение, очередь ошибок и восстановление старой копии, не только обычную сетевую попытку.

   </details>

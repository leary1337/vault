# Получатель Kafka

Получатель читает записи и отдельно сохраняет, откуда продолжать после перезапуска. Это сохранение называется **commit offset**. Оно само не выполняет платёж, запись SQL или другой эффект: порядок задаёт приложение.

## Две разные позиции

Текущая позиция клиента — номер следующей записи для получения. Сохранённая позиция группы — номер для продолжения после передачи части другому участнику или перезапуска. Они могут различаться, пока приложение обрабатывает уже полученные записи.

Для обработки с повторами порядок такой: получить → выполнить эффект → сохранить следующий offset. Падение перед последним шагом повторит эффект, поэтому нужен безопасный повтор. Сохранение раньше эффекта, наоборот, позволяет пропустить его после падения.

## Как выполнять параллельно

Один владелец управляет чтением, назначениями и сохранением позиций. Работу можно передать ограниченному набору исполнителей, но по каждой части сохранять только непрерывный обработанный префикс. Завершение записи 12 раньше 10 не разрешает перескочить через 10; ниже разобрана эта ситуация.

В Java `poll()` получает записи и участвует в жизненном цикле группы. Превышение `max.poll.interval.ms` может привести к потере назначения. Go-клиенты имеют свои механизмы чтения и heartbeat: проверяйте конкретный API, а не переносите Java-настройки буквально.

## Когда запись не удаётся обработать

Постоянную ошибку нельзя повторять бесконечно без задержки. Ограничьте попытки, отличайте временную ошибку от неверных данных. Отдельная очередь ошибок, DLQ, требует ответственного, срока хранения и процедуры повторной обработки. Перенос туда нарушает исходный строгий порядок.

Разность конца журнала и сохранённой позиции — отставание по номерам, не доказательство завершения внешнего эффекта. Измеряйте также возраст события и время обработки. `auto.offset.reset` применяется при отсутствии пригодной сохранённой позиции, а не перематывает каждое чтение.

## Параллельные workers и дырка

Из одной части получили записи 10, 11, 12. Исполнитель 12 закончил первым, 11 — вторым, 10 ещё работает. Сохранить 13 нельзя: после перезапуска запись 10 будет пропущена. Позиция должна остаться 10, пока не закончится весь непрерывный участок.

| Завершены | Можно commit next offset |
| --- | --- |
| Только 12 | 10 |
| 11 и 12 | 10 |
| 10,11,12 | 13 |

Предполагается, что всё до 10 уже обработано. Состояние завершений хранится отдельно для каждой части, и граница продвигается только без пропусков. Сохраняемый offset — **следующий** для обработки, а не последний завершённый.

```properties
# Java consumer: явное управление обработкой
enable.auto.commit=false
isolation.level=read_committed
max.poll.records=100
```

Настройки показаны для Java-клиента. В Go библиотека может отдельно хранить и сохранять позиции или делать это автоматически при вызове обработчика. Проверьте, когда именно её API считает запись обработанной и как обслуживает связь с группой.

При отзыве части остановите новую работу и ограниченно дождитесь или отмените начатую. Сохраните только успешный непрерывный участок. Старый исполнитель ещё способен завершить внешний эффект: inbox защищает повторное SQL-изменение, а порядок сущности может требовать проверки версии. Отмена контекста не откатывает выполненный HTTP-запрос.

# Идемпотентность: повтор запроса без второго эффекта

Клиент не всегда узнаёт, выполнилась ли операция: сервер мог сохранить заказ, а ответ потерялся. Идемпотентность позволяет повторить то же намерение без создания второго заказа.

## Как это работает

Клиент заранее выбирает устойчивый ID операции и передаёт его при каждой попытке. Сервер сохраняет ID, параметры и результат вместе с изменением данных. При повторе он возвращает сохранённый результат. Тот же ID с другими параметрами отклоняется: иначе одна операция незаметно превратится в другую.

Проверку существования ключа и создание результата нельзя разнести без защиты: два одновременных запроса оба увидят отсутствие. Уникальное ограничение и транзакция связывают эти шаги. Если эффект происходит у внешнего поставщика, локальной транзакции недостаточно; нужен такой же ID у поставщика и способ узнать исход.

Защита действует, пока хранится запись ключа. После её удаления очень поздний повтор способен создать новый эффект. Период хранения выбирают по реальным повторам и правилам продукта.

## Разобранный пример

Для создания объекта транзакция вставляет ключ операции, создаёт объект и сохраняет результат вместе. Если уникальный ключ уже занят, сервер читает параметры и прежний результат. В PostgreSQL Read Committed ON CONFLICT DO NOTHING может не вставить строку из-за конкурентной записи, ещё невидимой исходному снимку. Следующее чтение требует нового SQL-запроса с новым снимком; иной уровень изоляции может потребовать повторить транзакцию.

Запись «обрабатывается», сохранённая отдельно без восстановления, после падения способна навсегда занять ключ. Долгая внешняя операция требует сохранённого процесса, владельца, конечной аренды и проверки результата. Хранение ключа 24 часа даёт только 24-часовое окно защиты.

## Как занять ключ в PostgreSQL

Ниже фрагмент внутри транзакции приложения. Таблица `idempotency` должна иметь уникальное ограничение на пару `(scope, key)`. Параметры `$1`, `$2`, `$3` задаёт драйвер: область операции, устойчивый ключ намерения и хеш значимых параметров запроса.

```sql
INSERT INTO idempotency(scope, key, request_hash, status)
VALUES ($1, $2, $3, 'processing')
ON CONFLICT DO NOTHING;
```

Новая строка со статусом `processing` означает, что эта транзакция заняла ключ. Если пара уже существует, вставка ничего не делает. Код проверяет число вставленных строк, затем при повторе читает прежние параметры и результат; отличие хеша означает повторное использование ключа для другого намерения и отклоняется. Конкурентная вставка может ждать завершения другой транзакции.

Для короткой локальной операции создание объекта и сохранение окончательного результата происходят в этой же транзакции. При ошибке выполните `ROLLBACK`: резервирование ключа тоже отменится. Не подтверждайте отдельно `processing` без восстановления: падение оставит ключ занятым. При Read Committed после конфликта может понадобиться отдельный запрос с новым снимком, как разобрано выше. Если в таблице есть другие уникальные ограничения, задайте явную цель конфликта `(scope, key)`, чтобы не скрывать постороннюю ошибку.

## Проверь себя

1. Почему проверка ключа и создание объекта должны быть связаны?
2. Почему ключ нельзя просто удалить сразу после ответа?

<details>
<summary>Ответы</summary>

1. Иначе два запроса одновременно увидят отсутствие и создадут два объекта.
2. Клиент может не получить ответ и позднее повторить ту же операцию.

</details>

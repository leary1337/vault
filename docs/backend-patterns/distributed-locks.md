# Распределённая блокировка и устаревший владелец

Распределённая блокировка пытается назначить одного исполнителя работы среди нескольких процессов. Основная сложность: старый исполнитель может продолжить работу уже после того, как право передали новому.

## Как это работает

Обычно право выдаётся на ограниченный срок — аренду (lease). Исполнитель продлевает её, но сеть может пропасть, а процесс остановиться на долгую паузу. После истечения срока другой процесс получает право; первый ещё способен отправить запись. Поэтому проверки «блокировка была моей в начале» недостаточно.

Защиту конечной записи даёт возрастающий номер поколения — fencing token. Хранилище запоминает наибольший принятый номер и атомарно отклоняет более старые. Проверка должна выполняться там, где происходит эффект, а не только в сервисе блокировок. Случайный уникальный ID позволяет не удалить чужую блокировку, но не показывает, какой владелец новее.

Если задача сводится к изменению одной строки, условие по версии или уникальное ограничение БД часто проще отдельного распределённого замка.

## Разобранный пример

Исполнитель A получил номер 56 и остановился на 40 секунд. Его право истекло через 30 секунд. B получил номер 57 и записал новое состояние. Когда A оживёт, хранилище должно атомарно отклонить его номер 56. Проверка срока перед началом работы не защищает позднюю запись.

Номер обязан надёжно возрастать. Равный номер иногда допустим для нескольких действий одного владельца, поэтому он не заменяет ID операции. Случайная строка владения подходит для удаления только своей блокировки, но не для сравнения поколений. Если конечный ресурс не проверяет номера, защита от старого владельца отсутствует.

## Проверь себя

1. Почему истечение аренды не останавливает прежнего исполнителя?
2. Где проверяют номер поколения?

<details>
<summary>Ответы</summary>

1. Он мог быть в паузе или без связи и продолжить старую работу.
2. Атомарно на конечном ресурсе вместе с записью, которую защищают.

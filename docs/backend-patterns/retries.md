# Повторные попытки: когда помогают и когда вредят

Повтор полезен, если ошибка временная и новая попытка может закончиться успешно. Но при потерянном ответе первая попытка уже могла изменить данные.

## Как это работает

Различайте подтверждённый отказ и неизвестный исход. Ошибка проверки параметров не исчезнет от повтора. Разрыв сети после отправки платежа не доказывает, что платёж не выполнен: сначала выясняют результат по ID операции или повторяют по договорённости об идемпотентности.

Все попытки делят общий срок запроса. Каждая получает только часть оставшегося времени; ожидание между ними тоже расходует бюджет. Число попыток ограничивают, паузы увеличивают и добавляют случайный разброс, чтобы клиенты не ударили одновременно.

Назначьте один слой, отвечающий за повторы. Если API, прокси и библиотека каждый делают по три попытки, один пользовательский запрос способен превратиться в двадцать семь обращений к уже перегруженной зависимости.

## Разобранный пример

Учебный срок запроса — 800 мс. Оставляем 50 мс на ответ, первой попытке даём до 300 мс, паузе до 100 мс, а второй — не больше оставшегося. Значения зависят от сервиса.

При ошибке сериализации (serialization failure) БД отменила транзакцию: повторяют её целиком с новым снимком. При таймауте ответа на COMMIT результат уже мог сохраниться. Повтор без ID операции опасен. Статус 500 сам по себе не гарантирует безопасного повторения записи.

Три попытки в каждом из трёх вложенных слоёв могут дать 27 обращений. Даже случайные паузы не устраняют этот множитель; нужен один ответственный слой и общий предел попыток.

## Проверь себя

1. Доказывает ли таймаут, что запись не состоялась?
2. Почему повторять только последний SQL-запрос бывает неправильно?

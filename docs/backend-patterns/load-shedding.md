# Сброс лишней нагрузки

Когда сервис не успевает выполнять всю поступающую работу, часть запросов лучше быстро отклонить. Иначе очередь вырастет, и даже запросы, которые можно было обслужить, не дождутся ответа.

## Как это работает

При входе проверяем, есть ли свободный рабочий слот. Если слоты закончились, возвращаем понятный временный отказ и не начинаем дорогое обращение к БД. Время ожидания очереди тоже ограничивают: очередь из уже просроченных запросов расходует ресурсы без пользы.

Для важных операций можно оставить отдельный резерв. Например, отмена задания и проверка состояния должны работать даже при перегрузке обычных запросов. При отказе клиент обязан соблюдать паузы и собственный предел повторов, иначе быстрые отказы сами породят новый поток.

Количество слотов выбирают нагрузочным тестом по памяти, времени ответа и поведению зависимостей. Ограничение не восстанавливает сломанный сервис; оно удерживает ущерб в пределах, пока устраняют причину.

## Разобранный пример

При 1000 запросов/с и среднем времени 100 мс одновременно выполняется около ста запросов. Зависимость замедлилась до двух секунд: без ограничения их станет около двух тысяч. Предел в 150 слотов не ускоряет зависимость, зато ограничивает память и позволяет остальным быстро получить отказ. Это учебные числа для устойчивого потока, а не готовая настройка.

При общей временной перегрузке API может отвечать 503; при превышении квоты конкретного клиента — 429. Объясните клиенту политику повтора. Оставьте резерв для управления и диагностики. Прежде чем выполнять задачу из очереди, проверьте, не истёк ли её срок.

## Проверь себя

1. Зачем отказывать быстро вместо длинного ожидания?
2. Почему предел нельзя выбрать только по RPS?

<details>
<summary>Ответы</summary>

1. Чтобы не удерживать ресурсы на запросы, которые уже не дождутся полезного ответа.
2. Важны длительность и стоимость операций, память и мощность зависимостей.

</details>

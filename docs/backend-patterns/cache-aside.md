# Чтение через кэш: cache-aside

Кэш хранит копию часто запрашиваемых данных. При cache-aside приложение сначала проверяет эту копию и только при её отсутствии читает основную БД.

## Как это работает

Пользователь открывает объявление 42. В Redis проверяем ключ, содержащий ID объявления и арендатора. Если запись найдена, возвращаем её. Если нет — читаем БД, сохраняем копию с ограниченным сроком жизни и отвечаем. Этот срок называют TTL.

При изменении объявления сначала сохраняем новую версию в БД, затем удаляем копию из кэша. Порядок важен, но сам по себе не исключает гонку с другим читателем: пример ниже показывает почему. Для данных, где допустима секундная задержка, такой компромисс может быть приемлем. Для проверки прав или списания денег старая копия способна нарушить правило системы.

Когда кэш недоступен, все чтения идут в БД. Поэтому нужен предел одновременных загрузок и объединение одинаковых запросов, иначе отказ необязательного ускорителя превращается в отказ основного хранилища.

## Разобранный пример

Читатель A получил из БД версию 7. Писатель B сохранил версию 8 и удалил кэш. После этого A сохранил в кэше старую версию 7. При TTL 60 секунд она может жить ещё минуту от этой вставки. Удаление кэша после записи не исключило гонку.

Для чтения своей записи клиент может передать min_version=8. Сервер пропускает старую копию и обращается к источнику, уже применившему эту версию. Версия в имени ключа помогает лишь тогда, когда текущий номер достоверно известен.

При 10 000 чтений/с и 99% попаданий БД получает около 100/с. Потеря кэша даёт до 10 000/с: нужен план ограничения загрузок.

## Проверь себя

1. Почему удаление после записи не исключает старую копию?
2. Что требуется для гарантии чтения своей записи?

<details>
<summary>Ответы</summary>

1. Другой читатель способен вставить ранее прочитанное значение уже после удаления.
2. Проверять минимальную версию и при необходимости читать источник, способный её обслужить.

</details>

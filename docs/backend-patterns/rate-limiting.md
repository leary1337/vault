# Ограничение частоты запросов

Ограничитель частоты решает, сколько работы клиенту разрешено за период. Это защищает от злоупотребления и позволяет распределить ресурс между клиентами.

## Как это работает

Простое правило «100 запросов в минуту» хранит счётчик для календарной минуты. У него есть граница: клиент может отправить сто запросов в конце одной минуты и ещё сто в начале следующей.

Другая модель — ведро токенов (token bucket). Ведро имеет конечную ёмкость, токены поступают с заданной скоростью, запрос забирает один или несколько. Накопленный запас разрешает короткий всплеск, но средняя длительная скорость ограничена пополнением. Проверка и списание должны быть атомарными, иначе параллельные запросы потратят один запас несколько раз.

Локальный ограничитель считает только свой процесс. Для общего лимита нужны общий учёт или заранее распределённые квоты; при отказе этого учёта следует явно выбрать между отказом клиенту и временным превышением лимита.

## Разобранный пример

Фиксированное окно 100 запросов/мин разрешит сто в 12:00:59 и ещё сто в 12:01:00. Ограничение каждой минуты соблюдено, а за две секунды пришли двести.

Ведро с пополнением 100 токенов/мин и ёмкостью 100 разрешает такой запас один раз, затем выдаёт токены постепенно. Дорогой поиск может стоить 20 токенов, обычный GET — один. Если цена выше полной ёмкости, запрос не будет разрешён никогда: исправьте политику.

При реализации на Redis все ключи атомарной операции должны удовлетворять правилам размещения. Lua сам по себе не объединяет разные слоты Redis Cluster в общую транзакцию.

## Проверь себя

1. Чем ёмкость ведра отличается от скорости пополнения?
2. Что произойдёт с общим лимитом при десяти локальных счётчиках?

<details>
<summary>Ответы</summary>

1. Ёмкость задаёт разовый запас, скорость — длительную разрешённую нагрузку.
2. Без разделения квоты разрешённая суммарная нагрузка может увеличиться в десять раз.

</details>

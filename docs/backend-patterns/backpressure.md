# Обратное давление: как остановить рост очереди

Если задания поступают быстрее, чем обработчики успевают их выполнять, очередь растёт. Обратное давление (backpressure) заставляет отправителя замедлиться или получить отказ, когда получатель перегружен.

## Как это работает

Представьте загрузку фотографий: HTTP принимает файл, а рабочие горутины сжимают его. Канал с конечной ёмкостью ограничивает число ожидающих файлов. Когда он заполнен, отправитель либо ждёт свободного места до срока запроса, либо отвечает, что сервис занят. Оба варианта требуют ограничить число самих отправителей: тысяча горутин, ожидающих канал, тоже занимает память.

Ограничение очереди защищает ресурс, но не делает обработку быстрее. У задачи должен быть срок пригодности: просроченную фотографию не нужно сжимать, если клиент уже отменил операцию. Подтверждение записи в канал означает только приём в память; после падения процесса эта задача исчезнет. Для обещания пережить перезапуск нужен сохраняемый журнал или очередь.

## Разобранный пример

Очередь вмещает 1000 задач. Каждую секунду поступает 500, завершается 300: за секунду добавляются 200, а пустая очередь заполнится за 5 секунд. Если допустимое ожидание всего 200 мс, при постоянной скорости обработки 300/с очередь примерно из 60 задач уже соответствует этому ожиданию. Это оценка, а не гарантия времени для каждого задания.

В Go отправляйте задачу через select с ветками передачи, отмены контекста и быстрого отказа. Если отправителю разрешено ждать, быстрый отказ можно убрать, но отмена остаётся. Не запускайте отдельную горутину только ради ожидающей отправки: так ограниченная очередь превращается в неограниченное число ожидающих горутин. Получатель отдельно проверяет срок уже принятой задачи.

## Приём задачи без бесконечного ожидания

Фрагмент находится внутри функции, возвращающей `error`. `jobs` — канал задач с конечной ёмкостью, `job` — очередная задача, `ctx` — контекст запроса, `ErrBusy` — определённая приложением ошибка перегрузки.

```go
select {
case jobs <- job:
    // Задача принята в память; это не сохранение после перезапуска.
case <-ctx.Done():
    return ctx.Err()
default:
    return ErrBusy
}
```

Если в канале есть место или получатель уже готов, первая ветка принимает задачу и код продолжается ниже `select`. Это ещё не сохранённый результат: задача пока находится в памяти. Вторая ветка возвращает причину отмены. Если ни передача, ни отмена не готовы, `default` немедленно возвращает отказ, а не создаёт ещё одного ожидающего отправителя.

Если отправителю разрешено ждать свободное место, убирают `default`, сохраняя отмену. Когда передача и отмена готовы одновременно, `select` может выбрать любую: строгого приоритета отмены нет. Уже принятую задачу получатель проверяет отдельно по сроку, а признанный успешным приём не становится автоматически отменённым.

## Проверь себя

1. Почему ограниченный канал не всегда ограничивает память?
2. Что подтверждает успешная отправка в канал?

<details>
<summary>Ответы</summary>

1. Перед ним могут без ограничения накапливаться горутины и удерживаемые ими данные.
2. Приём значения в память, а не сохранение результата после перезапуска.

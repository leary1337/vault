# Сага: согласование нескольких отдельных операций

Покупка может затрагивать склад, платёжный сервис и доставку. Общей транзакции между ними часто нет. Сага сохраняет ход этой работы и выполняет отдельные шаги с предусмотренным восстановлением.

## Как это работает

После резервирования товара запускается оплата. Если оплата окончательно отклонена, выполняется отдельная операция освобождения резерва. Это компенсация, а не откат времени: отправленное письмо нельзя забрать, а возврат денег создаёт новый платёжный факт.

Состояние процесса сохраняют перед продолжением. После перезапуска исполнитель видит, какой шаг завершён, какой неизвестен и что проверить. Команды получают устойчивые ID, поскольку могут отправляться повторно. Переходы состояния защищают версией от двух одновременных исполнителей.

Компенсация тоже может ошибиться. Для такого состояния нужны последующие попытки или ручной разбор с ответственным. Пока процесс не завершён, правила чтения должны честно отражать промежуточное состояние, например «оплата уточняется».

## Разобранный пример

Покупка проходит резерв товара, авторизацию оплаты и подтверждение. Храним состояние процесса, версию и ID каждой команды. Переход проверяет ожидаемую версию, чтобы два исполнителя не продолжили один шаг независимо.

Если неизвестно, списались ли деньги, сначала узнаём исход у поставщика по ID операции. Раннее освобождение товара и повторное списание могут создать оплату без покупки. Компенсация освобождает конкретный reservation ID, а не любой резерв товара: иначе затронет другой заказ.

Неудачная компенсация получает явное состояние ручного разбора, ответственного и срок. Возврат денег — новый финансовый факт; отправленное письмо отменить невозможно.

## Проверь себя

1. Чем компенсация отличается от отката SQL-транзакции?
2. Почему нужно сохранять состояние процесса?

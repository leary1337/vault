# Метрики: измерять поведение системы

Метрика — числовое наблюдение во времени: число запросов, занятые соединения или длительность ответа. Она помогает увидеть масштаб проблемы, но обычно не объясняет историю конкретного запроса.

## Как это работает

Счётчик только накапливает события, например завершённые запросы. Его абсолютное значение зависит от времени запуска, поэтому для интенсивности считают изменение за интервал. Измеритель текущего значения показывает величину прямо сейчас, например длину очереди. Гистограмма распределяет наблюдения длительности по границам и позволяет оценивать долю медленных ответов.

Метки разделяют ряды по операции, версии и статусу. Каждый новый набор меток создаёт отдельный ряд. ID пользователя или произвольный URL способны породить миллионы рядов, поэтому используют шаблоны маршрутов и конечные наборы значений.

Метка полезна, когда помогает принять решение. Для успешности нужны и хорошие, и все учитываемые события. Отсутствие данных отличается от нуля: сломанный сбор не должен выглядеть как полное отсутствие ошибок.

## Разобранный пример

Счётчик вырос с 10 000 до 10 600 за минуту: средняя скорость — 10 запросов/с. После перезапуска он упадёт; rate в Prometheus учитывает сбросы.

Если гистограмма за минуту содержит 1000 запросов, из которых 950 уложились в 300 мс, доля быстрых — 95%. Для суммарной оценки объединяют согласованные корзины экземпляров, а не усредняют их p99. Экземпляр со ста запросами не должен иметь такой же вес, как экземпляр с десятью тысячами.

## Запросы Prometheus для времени ответа

Ниже примеры для **классической гистограммы** Prometheus. Приложение заранее экспортирует `http_request_duration_seconds_bucket` и `_count`. Библиотека метрик добавляет `le` — верхнюю границу накопительной корзины. `route` содержит шаблон маршрута, например `/ads/{id}`, а не каждый реальный ID. Метка `job="ads"` выбирает один сервис; в вашем окружении её имя и значение могут быть другими.

```promql
# p99 всех экземпляров, отдельно для каждого шаблона маршрута.
histogram_quantile(0.99,
  sum by (le, route) (
    rate(http_request_duration_seconds_bucket{job="ads"}[5m])
  )
)

# Доля ответов не медленнее 300 мс при существующей корзине le="0.3".
sum by (route) (
  rate(http_request_duration_seconds_bucket{job="ads",le="0.3"}[5m])
)
/
sum by (route) (
  rate(http_request_duration_seconds_count{job="ads"}[5m])
)
```

`[5m]` берёт последние пять минут. `rate` оценивает скорость прироста счётчика за это окно и учитывает сброс при перезапуске. Сначала считается скорость каждого ряда, затем `sum` объединяет экземпляры. В первом запросе обязательно сохраняется `le`: без границ корзин распределение не восстановить. `histogram_quantile(0.99, ...)` оценивает порог p99 в **секундах**. Это оценка по корзинам, а не точное время конкретного запроса и не обещание следующему клиенту.

Второй запрос делит скорость запросов, уложившихся в 0,3 секунды, на скорость всех наблюдений. Например, 95 быстрых из 100 дают `0.95`, то есть 95%. Корзина `le="0.3"` должна действительно быть настроена при измерении; отсутствие ряда не означает ноль быстрых ответов. Эти запросы учитывают наблюдения длительности, а не автоматически только успешные статусы. Для совмещённой цели успеха и скорости согласуйте набор учитываемых событий.

При отсутствии запросов знаменатель равен нулю: полученное неопределённое значение нельзя называть отказом сервиса. Отсутствие самих метрик тоже диагностируется отдельно. Значения `route`, статусов и иных меток должны оставаться ограниченными: миллион ID создаст миллион наборов рядов и сделает сбор дорогим.

## Проверь себя

1. Почему нельзя считать ID пользователя обычной меткой?
2. Как агрегировать время по экземплярам?

<details>
<summary>Ответы</summary>

1. Число уникальных наборов меток растёт вместе с пользователями и перегружает хранение.
2. Объединять число наблюдений и совместимые корзины; не усреднять готовые процентили.

</details>

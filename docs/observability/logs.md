# Логи: записи событий, которые можно связать

Лог описывает отдельное событие: операция началась, проверка не прошла или произошёл отказ зависимости. Хороший лог помогает восстановить обстоятельства без догадок.

## Как это работает

Используйте структурированные поля: время с часовым поясом, уровень, операция, код ошибки, версия и ID запроса или трассировки. Тогда записи можно искать и связывать, а не разбирать человеческую фразу регулярным выражением.

Сообщение ошибки отвечает, какое действие не выполнено и почему. Не записывайте одно и то же событие на каждом слое: нижний слой возвращает причину, а слой, принимающий решение, добавляет контекст. При ожидаемом отказе пользователю уровень ERROR часто создаёт шум.

Пароли, токены и полные тела запросов не должны попадать в журнал. Объём ограничивают, поля очищают и определяют срок хранения. Если очередь отправки логов заполнена, политика потери или ожидания должна быть явной: диагностика сама не должна незаметно остановить сервис.

## Разобранный пример

Для неудачного сохранения объявления полезны operation=update_ad, error_code=version_conflict, ad_id=42, request_id и версия приложения. SQL с пользовательскими значениями и токеном авторизации не нужен.

ID запроса связывает записи одной попытки. ID операции связывает повторы того же намерения: это разные задачи. В распределённом потоке порядок по времени нескольких машин может быть неточным, поэтому используют также причинные связи и версии. При массовом повторе одной ошибки ограничьте количество записей, сохранив счётчик общего числа и репрезентативные детали.

## Структурированная запись

Учебный пример события завершения одной операции:

```json
{"level":"ERROR","service":"ads","operation":"update_price","outcome":"db_timeout","duration_ms":450,"trace_id":"example-trace","attempts":2}
```

`level` — важность события, `service` — источник, `operation` — действие. `outcome` — устойчивый код исхода, здесь таймаут обращения к БД. `duration_ms` измеряет длительность в миллисекундах в заранее выбранной границе; `attempts` считает попытки этой операции. `trace_id` связывает диагностику, но не заменяет ключ намерения для защиты от повторов. В примере он условный.

Запись позволяет найти все таймауты изменения цены и сравнить их с версией приложения и длительностью. Добавьте отметку времени с часовым поясом и другие нужные поля в реальном формате логгера. Содержание SQL, пароль и токен не нужны. Здесь ERROR выбран для неуспешной операции; ожидаемый отказ клиенту из-за параметров может иметь другой уровень.

## Проверь себя

1. Почему один журнал ошибок на каждом слое вреден?
2. Чем ID операции отличается от ID запроса?

<details>
<summary>Ответы</summary>

1. Дубли увеличивают шум и расходы, хотя описывают один отказ.
2. Первый сохраняется при повторе намерения, второй может обозначать отдельную попытку.

</details>

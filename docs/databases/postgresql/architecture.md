# Архитектура PostgreSQL

PostgreSQL — сервер, которому приложение отправляет SQL. Он разбирает запрос, выбирает способ получения строк и возвращает результат. Каждое прямое соединение обслуживает отдельный серверный процесс, поэтому тысяча соединений требует ресурсов даже тогда, когда не делает тысячу полезных запросов.

## Что происходит с запросом

Для `SELECT ... WHERE id=42` сервер сначала проверяет синтаксис, находит таблицу и типы колонок. Представления разворачиваются в запросы к исходным таблицам. Планировщик сравнивает способы чтения: пройти таблицу или найти адрес через индекс. Исполнитель читает данные выбранным способом и проверяет, видна ли версия строки текущему запросу — это [MVCC](mvcc.md).

Подготовленный запрос может иметь план под конкретное значение параметра или общий план. Общий план экономит работу планировщика, но не всегда одинаково хорош для редкого клиента с одним заказом и крупного клиента с миллионом заказов. Различие проверяют через `EXPLAIN`, а не по самому факту использования prepared statement.

## Где находятся данные и память

Таблица хранится в файлах, разбитых на страницы; обычный размер страницы — 8 КиБ. Найденные страницы попадают в общий кэш PostgreSQL (`shared_buffers`). Операционная система тоже кэширует файлы. Строки таблицы и индекс хранятся отдельно: адрес из индекса ещё не всегда означает, что данные уже прочитаны.

`work_mem` ограничивает память **отдельной операции** сортировки или хеширования. Один запрос может содержать несколько таких операций и несколько параллельных исполнителей. Поэтому установка `work_mem=16MB` не означает «весь запрос потребляет максимум 16 МБ». Для хеширования дополнительно учитывается `hash_mem_multiplier`.

## Почему нужны фоновые процессы

Изменённая страница сначала может оставаться в памяти. [Журнал изменений: WAL](wal.md) сохраняет журнал изменений, позволяющий восстановить её после аварии. Процесс контрольных точек записывает накопленные страницы и ограничивает объём восстановления; фоновая запись сглаживает нагрузку. [Autovacuum](vacuum.md) очищает ненужные версии и обновляет статистику. Процессы репликации передают и применяют журнал на копиях сервера.

Обычное копирование каталога работающей базы не гарантирует согласованную резервную копию: файлы меняются во время копирования. Используйте штатный способ резервирования вместе с необходимым WAL.

## Картинка: путь SELECT

```mermaid
flowchart LR
    App[Приложение] --> Backend[Процесс соединения]
    Backend --> Parse[Разбор SQL и имён]
    Parse --> Plan[Выбор плана]
    Plan --> Exec[Выполнение]
    Exec --> Cache[Общий кэш страниц]
    Cache --> Disk[Файлы таблиц и индексов]
    Exec --> Result[Результат]
```

Запрос по id находит адрес через индекс, читает страницу и проверяет видимость строки. Наличие страницы в памяти не отменяет проверку снимка.

```sql
SHOW block_size;
SHOW work_mem;
SELECT pid,state,wait_event_type,wait_event
FROM pg_stat_activity WHERE datname=current_database();
```

`SHOW block_size` возвращает размер страницы в байтах: обычно 8192. `SHOW work_mem` показывает текущий предел отдельной операции. Запрос `pg_stat_activity` возвращает процессы текущей базы: `pid` — идентификатор, `state` — состояние, `wait_event_type` — класс ожидания, `wait_event` — конкретное ожидание. Строка с ожиданием блокировки объясняет задержку даже при свободном процессоре; увеличение процессоров не освобождает блокировку.

## Проверь себя

1. **Почему увеличение max_connections может замедлить базу?**

   <details>
   <summary>Ответ</summary>

   Появится больше процессов и конкурентов за память, процессор, диск и блокировки; мощность сервера не выросла.

   </details>

2. **Что проверить перед увеличением work_mem?**

   <details>
   <summary>Ответ</summary>

   Число операций сортировки и хеширования, параллельных исполнителей и активных запросов; действительно ли работа уходит на диск.

   </details>

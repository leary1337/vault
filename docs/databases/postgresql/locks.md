# Блокировки PostgreSQL

Блокировка заставляет конфликтующую операцию ждать. При изменении одного баланса это позволяет одному писателю закончить раньше другого. Обычный `SELECT` благодаря MVCC часто читает старую версию, но `SELECT FOR UPDATE` специально блокирует выбранные строки.

## Что блокируется

Строковые режимы `FOR UPDATE`, `FOR NO KEY UPDATE`, `FOR SHARE`, `FOR KEY SHARE` разрешают разные комбинации читателей и писателей. Защита ключа от удаления и изменения не обязана запрещать обновление остальных полей. Выбирайте режим по требуемой защите.

Блокировки таблиц защищают также схему. `ACCESS EXCLUSIVE`, необходимая многим DDL-командам, конфликтует даже с обычным чтением. Ожидающая миграция способна собрать очередь новых запросов; `lock_timeout` прекращает слишком долгое получение блокировки.

## Цикл ожиданий

A держит строку 1 и ждёт 2. B держит 2 и ждёт 1. Это **взаимная блокировка**, deadlock. PostgreSQL разрывает цикл ошибкой `40P01` одной транзакции. Длительное ожидание без цикла — другая ситуация. `deadlock_timeout` задаёт задержку проверки цикла, не общий предел ожидания.

При повторе откатите всю транзакцию. Если все участники захватывают ресурсы в одном порядке, например сначала меньший id, такой цикл предотвращается.

## Очереди и прикладные блокировки

`SKIP LOCKED` позволяет пропустить занятые задачи. Захват и изменение статуса происходят в одной короткой транзакции. После выдачи задачи обработчик может упасть: нужны срок владения, возврат зависшей задачи и безопасный повтор эффекта.

Advisory lock защищает выбранный приложением ключ, только если все участники соблюдают этот протокол. Блокировки сессии и транзакции имеют разный срок жизни, особенно за пулом соединений. Оптимистическая проверка `UPDATE ... WHERE version=old_version` позволяет не удерживать блокировку между предварительным чтением и записью; конфликт обнаруживается по нулю изменённых строк. Сам `UPDATE` всё ещё может ждать другую транзакцию, меняющую ту же строку.

Найдите ожидающий процесс в `pg_stat_activity`, блокирующих через `pg_blocking_pids`, конкретные блокировки в `pg_locks`. Затем выясните, почему ресурс удерживался долго.

## Воспроизвести deadlock

```sql
CREATE TABLE lock_demo(id integer PRIMARY KEY,value integer NOT NULL);
INSERT INTO lock_demo VALUES (1,0),(2,0);
```

| Шаг | A | B |
| --- | --- | --- |
| 1 | BEGIN; UPDATE lock_demo SET value=value+1 WHERE id=1 | |
| 2 | | BEGIN; UPDATE lock_demo SET value=value+1 WHERE id=2 |
| 3 | UPDATE lock_demo SET value=value+1 WHERE id=2 → ждёт | |
| 4 | | UPDATE lock_demo SET value=value+1 WHERE id=1 → ждёт |

После обнаружения цикла одна транзакция получает 40P01; приложение делает rollback и повтор целиком. Если обе захватывают id=1 затем id=2, цикл предотвращён. deadlock_timeout задаёт задержку проверки цикла, а не максимальное время любого ожидания.

```mermaid
flowchart LR
    A[A удерживает строку 1] -->|ждёт строку 2| B[B удерживает строку 2]
    B -->|ждёт строку 1| A
```

После сохранения выдачи задачи обработчик может упасть. Нужны срок владения и процесс, возвращающий просроченные задачи в очередь. Повторный эффект должен быть безопасным: `SKIP LOCKED` защищает выбор занятых строк, не всю последующую работу. Для миграций ограничивайте время ожидания блокировки через `lock_timeout`, чтобы не создавать долгую очередь.

## Найти, кто удерживает ресурс

Диагностический запрос выполняется в отдельной сессии, пока другая операция ждёт:

```sql
SELECT a.pid,
       a.query,
       a.wait_event_type,
       a.wait_event,
       pg_blocking_pids(a.pid) AS blockers
FROM pg_stat_activity AS a
WHERE cardinality(pg_blocking_pids(a.pid)) > 0;
```

Каждая строка — ожидающий процесс: `pid` идентифицирует его, `query` показывает запрос, `wait_event_type` и `wait_event` — вид ожидания, `blockers` — массив номеров блокирующих процессов. Пустой результат означает отсутствие найденных блокировщиков в момент проверки, а не отсутствие всех видов ожидания. Полный текст чужих запросов зависит от прав; блокирующий процесс может простаивать внутри незавершённой транзакции. Его не следует завершать до выяснения назначения и последствий отката.

## Выдать задачу одному обработчику

Самостоятельный учебный пример: две готовые задачи и одна уже выданная. Выполняйте блок захвата из двух сессий: пока первая удерживает строку, вторая пропускает её.

```sql
CREATE TABLE lock_jobs(
    id integer PRIMARY KEY,status text NOT NULL,
    claimed_until timestamptz
);
INSERT INTO lock_jobs(id,status) VALUES (1,'ready'),(2,'ready'),(3,'running');
BEGIN;
WITH picked AS (
    SELECT id FROM lock_jobs WHERE status='ready'
    ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED
)
UPDATE lock_jobs AS j
SET status='running',claimed_until=now()+interval '1 minute'
FROM picked WHERE j.id=picked.id
RETURNING j.id,j.claimed_until;
COMMIT;
```

Без конкуренции возвращается задача 1 и время окончания владения. Выбор строки и смена статуса входят в одну транзакцию; после COMMIT другой обработчик уже не выбирает её как готовую. Сама работа начинается после сохранения выдачи. Срок в минуту учебный: для долгой работы нужны продление и защита от запоздавшего обработчика, а для падения — возврат просроченных задач. `SKIP LOCKED` пропускает блокировки строк, но не исключает ожидание блокировки таблицы и не даёт согласованный отчёт по очереди.

## Обнаружить изменение после чтения

Самостоятельная таблица хранит номер версии документа:

```sql
CREATE TABLE lock_documents(
    id integer PRIMARY KEY,body text NOT NULL,version integer NOT NULL
);
INSERT INTO lock_documents VALUES (1,'старый текст',1);
UPDATE lock_documents SET body='правка A',version=version+1
WHERE id=1 AND version=1 RETURNING version;
UPDATE lock_documents SET body='правка B',version=version+1
WHERE id=1 AND version=1 RETURNING version;
```

Первый UPDATE возвращает 2; второй не возвращает строку, потому что версия 1 уже устарела. Клиент перечитывает документ и согласует правку вместо молчаливого затирания. В приложении текст, id и прочитанная версия передаются параметрами. Ноль строк также возможен при удалении документа. Сам UPDATE всё равно получает блокировку на время выполнения; этот подход убирает удержание блокировки между предварительным чтением и записью. Правила между несколькими строками требуют отдельной защиты.

1. **Чем взаимная блокировка отличается от долгого ожидания?**

   <summary>Ответ</summary>

   Есть цикл: каждый ждёт ресурс другого. Длинная очередь без цикла сама не вызывает 40P01.

   </details>

2. **Что не решает SKIP LOCKED?**

   <details>
   <summary>Ответ</summary>

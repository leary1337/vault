# Транзакции

Транзакция объединяет изменения: либо база сохраняет их вместе через `COMMIT`, либо отменяет через `ROLLBACK`. Списание и зачисление денег должны входить в одну транзакцию. Без явного `BEGIN` PostgreSQL выполняет каждую команду отдельно.

## Атомарность не заменяет правила

Два `UPDATE` могут атомарно создать отрицательный баланс или зачислить без списания. Нужно проверить положительную сумму, оба счёта и остаток. Ограничения, условия обновления и порядок блокировок защищают разные части правила.

Передавайте один объект транзакции всем операциям. В Go запрос через `db` вместо `tx` может уйти на другое соединение. Держите транзакцию короткой: ожидание внешней сети продлевает удержание блокировок и соединения.

## Что происходит после ошибки

После ошибки явная транзакция не выполняет следующие обычные команды: нужен `ROLLBACK`. Если заранее создан `SAVEPOINT`, можно откатить участок до него и продолжить. Это точка внутри той же транзакции, не отдельно сохранённая операция.

При `40001` (конфликт сериализации) и `40P01` (взаимная блокировка) повторяют всю транзакцию, включая чтения. Ограничьте число попыток и добавьте случайную задержку, чтобы конкуренты не столкнулись снова.

## Неизвестный исход сохранения

Соединение может оборваться после сохранения `COMMIT`, но до ответа клиенту. Слепой повтор перевода опасен. Сохраните уникальный ключ операции и результат вместе с переводом: следующий запрос сможет найти прежний результат.

`ROLLBACK` не отменяет отправленное письмо и выданный номер sequence. Большинство DDL транзакционно, но, например, `CREATE DATABASE` и `VACUUM` не разрешены внутри обычного блока транзакции.

## Перевод с проверкой остатка

```sql
CREATE TABLE transfer_accounts(
    id integer PRIMARY KEY,balance bigint NOT NULL CHECK(balance>=0)
);
INSERT INTO transfer_accounts VALUES (1,500),(2,100);
BEGIN;
SELECT id FROM transfer_accounts WHERE id IN (1,2) ORDER BY id FOR UPDATE;
UPDATE transfer_accounts SET balance=balance-200
WHERE id=1 AND balance>=200 RETURNING balance;
-- продолжать только если возвращена одна строка; иначе ROLLBACK
UPDATE transfer_accounts SET balance=balance+200 WHERE id=2;
COMMIT;
SELECT * FROM transfer_accounts ORDER BY id;
-- (1,300), (2,300)
```

Для реального перевода проверьте положительную сумму, существование обоих счетов и одинаковый порядок захвата для всех writers. CHECK не исключает зачисление без списания.

В коде вызывающего после `BeginTx` предусмотрите откат при выходе с ошибкой и проверьте результат `Commit`. Уникальный ключ перевода хранится в той же транзакции, чтобы неизвестный исход можно было проверить, а не повторить списание вслепую. Пропуски identity допустимы: выданные номера не обязаны откатываться.

## Отменить необязательный участок через SAVEPOINT

Самостоятельный пример: основное событие сохраняется, а неудачная попытка добавить дополнение откатывается. Команды показаны для интерактивной сессии, которая продолжает ввод после ожидаемой ошибки.

```sql
CREATE TABLE tx_notes(id integer PRIMARY KEY,body text NOT NULL);
BEGIN;
INSERT INTO tx_notes VALUES (1,'основное событие');
SAVEPOINT optional_note;
INSERT INTO tx_notes VALUES (1,'дополнение');
-- ожидаемая ошибка 23505: такой id уже существует
ROLLBACK TO SAVEPOINT optional_note;
INSERT INTO tx_notes VALUES (2,'исправленное дополнение');
RELEASE SAVEPOINT optional_note;
COMMIT;
SELECT * FROM tx_notes ORDER BY id;
```

Результат — строки 1 и 2 с разными текстами. Точка создана после основного события, поэтому откат к ней сохраняет первую вставку и снимает состояние ошибки второй. RELEASE убирает точку отката, но ничего отдельно не сохраняет: окончательное сохранение происходит через COMMIT. В приложении нужно явно обработать допустимую ошибку и выполнить откат к точке; клиент с режимом остановки при первой ошибке этот пример целиком не продолжит. SAVEPOINT не заменяет повтор всей транзакции при конфликте сериализации.

# Уровни изоляции PostgreSQL

Изоляция определяет, какие последствия параллельных транзакций допустимы. Представьте двух дежурных: каждый проверяет, что второй на смене, и снимает себя с дежурства. По отдельности обе операции правильны, вместе оставляют смену без дежурного.

## Что увидят повторные чтения

**Read Committed**, режим по умолчанию, получает новый снимок данных для каждой команды. Между двумя `SELECT` другой клиент может сохранить изменения, поэтому ответы будут различаться. Название `Read Uncommitted` PostgreSQL принимает, но выполняет как Read Committed: незавершённые изменения чужой транзакции не видны.

**Repeatable Read** фиксирует снимок с первой команды, не являющейся управлением транзакцией. Повторные чтения видят прежний набор, включая защиту от появления новых подходящих строк. Но две транзакции всё ещё могут обновить разные строки и совместно нарушить правило — как в примере дежурных.

**Serializable** разрешает лишь результат, который мог бы возникнуть при некотором последовательном порядке успешно завершённых транзакций. PostgreSQL обнаруживает опасные зависимости чтений и записей. Вместо неверного результата одна операция может получить `40001`; приложение повторяет **всю** транзакцию, включая чтения.

## Какие ошибки не стоит путать

Неповторяемое чтение — одна строка изменилась между чтениями. Фантом — появился или исчез подходящий набор строк. Потерянное обновление — два клиента прочитали 10, вычислили 11 и оба записали 11 вместо 12. Атомарный `UPDATE ... SET value=value+1` решает этот пример; чтение и запись отдельно — нет.

Нарушение общего правила разными записями называется **write skew**. Блокировка одной обновляемой строки не обязательно защищает правило над несколькими строками. Выберите Serializable, явно блокируемый общий объект или другой протокол, который защищает всё правило.

## Цена строгого режима

Serializable использует SSI: наблюдает зависимости, а специальные блокировки чтения (`SIRead`) служат для обнаружения конфликтов, не для обычного ожидания писателей. Возможны дополнительные отказы и повторы. Они должны быть ограничены по числу и времени; внешнее действие, например платёж, нельзя слепо повторять вместе с SQL.

## Write skew: оба дежурных ушли

Правило: хотя бы один врач остаётся на дежурстве.

```sql
CREATE TABLE duty(name text PRIMARY KEY,on_call boolean NOT NULL);
INSERT INTO duty VALUES ('Аня',true),('Борис',true);
```

В двух соединениях начните BEGIN ISOLATION LEVEL REPEATABLE READ и выполните SELECT count(*) FROM duty WHERE on_call до обновлений.

| Шаг | A | B |
| --- | --- | --- |
| 1 | Читает 2 дежурных | Читает 2 дежурных |
| 2 | UPDATE duty SET on_call=false WHERE name='Аня' | |
| 3 | | UPDATE duty SET on_call=false WHERE name='Борис' |
| 4 | COMMIT | COMMIT |

Обе изменяли разные строки. Конфликта одной строки нет; итог — 0 дежурных.

```mermaid
flowchart LR
    A[A читает Бориса] --> B[B выключает Бориса]
    B --> C[B читает Аню]
    C --> D[A выключает Аню]
    D --> A
```

Это цикл зависимостей чтение-запись, а не ожидания блокировок. Сбросьте строки в true и повторите обе транзакции с SERIALIZABLE: одна получит 40001 при записи или commit. Повтор её целиком увидит одного дежурного, и приложение должно отказать в уходе. Таблица сценария иллюстрирует решения приложения; SQL UPDATE сам не содержит условной проверки количества.

Альтернатива — блокировать общую строку смены всеми писателями и проверять правило после захвата. FOR UPDATE только собственной строки не помогает. SSI может отменять больше случаев, чем минимально необходимо; измеряйте частоту повторов. 40001 также бывает в Repeatable Read при конфликте обновления, а 40P01 обозначает цикл ожидания блокировок. Повторяется вся транзакция, но профилактика причин различается.

# Пагинация

Пагинация выдаёт большой результат порциями. Чтобы продолжать с правильного места, порядок должен однозначно определять положение каждой строки. Если даты совпадают, добавьте уникальный id: `ORDER BY created_at DESC,id DESC`.

## Почему номер страницы дорожает

`LIMIT 50 OFFSET 5000` означает: найти строки в нужном порядке, пропустить 5000 и вернуть 50. Чем дальше страница, тем больше работа. Новые записи и удаления между запросами могут сдвинуть страницы: появятся повторы или пропуски.

## Продолжение по последнему ключу

Пагинация по ключу (keyset) хранит последнюю пару `(created_at,id)` как курсор. Для убывающего порядка следующая порция выбирает пары меньше неё: `WHERE (created_at,id)<($1,$2)`. Индекс с тем же порядком помогает перейти к диапазону, не отсчитывая предыдущие строки.

Курсор — данные для продолжения, не разрешение на доступ. Привяжите его к фильтрам и проверяйте права на каждой странице. Если клиенту нельзя менять значения, подпишите курсор. Для смешанных направлений сортировки и `NULL` требуется отдельное условие.

## Где заканчивается гарантия

Keyset защищает от сдвига порции новыми строками выше курсора, но не создаёт неизменный снимок. Изменение даты старой строки может перенести её через границу. Верхняя граница не защищает от удаления и изменения старых строк.

Для точного экспорта используйте отдельную задачу со снимком или материализованным составом данных. Не оставляйте веб-транзакцию открытой, пока человек читает страницу. Произвольный номер страницы и точный `COUNT(*)` имеют отдельную цену; иногда достаточно кнопки «ещё» без общего числа.

## Курсор при одинаковых датах

```sql
CREATE TABLE page_posts(id integer PRIMARY KEY,created_at timestamptz NOT NULL);
INSERT INTO page_posts VALUES
(1,'2026-10-01 UTC'),(2,'2026-10-01 UTC'),(3,'2026-10-02 UTC');
CREATE INDEX page_posts_cursor ON page_posts(created_at DESC,id DESC);
SELECT * FROM page_posts ORDER BY created_at DESC,id DESC LIMIT 2;
-- ids: 3,2; курсор ('2026-10-01 UTC',2)
SELECT * FROM page_posts
WHERE (created_at,id)<(timestamptz '2026-10-01 UTC',2)
ORDER BY created_at DESC,id DESC LIMIT 2;
-- id: 1
```

Индекс `page_posts_cursor` хранит тот же порядок даты и id, что обе страницы. Он позволяет искать диапазон ниже курсора; на трёх строках планировщик всё равно может предпочесть чтение таблицы.

Новая запись выше курсора не сдвинет следующую порцию как OFFSET. Но изменение даты старой записи может перенести её через курсор: keyset не равен снимку. Верхняя граница исключает новые более высокие ключи, но не фиксирует изменения/удаления старых строк. Строгий export требует ограниченного по времени snapshot или материализации состава данных.

Для score DESC,id ASC сравнение пары через < неверно: используйте score<last_score OR (score=last_score AND id>last_id). При NULL определите порядок и условия отдельно. Курсор привяжите к фильтрам; проверка доступа выполняется на каждой странице.

1. **Почему одной даты недостаточно для курсора?**

   <details>
   <summary>Ответ</summary>

   При равных датах порядок не однозначен. Уникальный id различает строки и задаёт точную границу.

   </details>

2. **Создаёт ли верхняя граница неизменный экспорт?**

   <details>
   <summary>Ответ</summary>

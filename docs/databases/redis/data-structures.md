# Структуры данных Redis

Redis хранит значения разных типов. Тип выбирают по действиям: увеличить счётчик, проверить наличие пользователя, получить рейтинг или выдать запись обработчику. В одном ключе находится значение одного типа; неподходящая команда вернёт `WRONGTYPE`.

## Что выбрать для задачи

| Тип | Пример действия |
| --- | --- |
| String | `INCR` атомарно увеличивает счётчик; `SET` сохраняет готовый объект целиком |
| Hash | `HSET` меняет отдельное поле объекта, `HINCRBY` — числовое поле |
| List | Добавление и извлечение с концов списка; простая временная очередь |
| Set | Уникальные теги и проверка принадлежности через `SISMEMBER` |
| Sorted Set | Участники со значением score: рейтинг и выбор диапазона |
| Stream | Журнал записей с идентификаторами и отслеживанием обработки |

## Почему одна команда лучше двух

Два клиента, прочитавшие счётчик 0, могут оба записать 1. Две команды `INCR` дадут 2, потому что каждое увеличение выполняется целиком относительно других команд сервера. Несколько отдельных запросов не становятся одной атомарной операцией автоматически.

`MULTI/EXEC` группирует команды, но ошибка выполнения одной не откатывает уже выполненные остальные. `WATCH` разрешает выполнить блок лишь при неизменности наблюдаемых ключей. Lua-скрипт выполняет связанное действие без вмешательства других команд, но долгий скрипт задерживает сервер.

## Что нужно знать о Streams

Группа обработчиков получает записи через `XREADGROUP`. Выданная, но не подтверждённая запись находится в списке ожидающих подтверждения — PEL. После успешного эффекта обработчик делает `XACK`. Если он упал раньше подтверждения, другой должен забрать запись и безопасно повторить работу. `XAUTOCLAIM` помогает возвращать зависшие записи. Ограничивайте размер журнала и наблюдайте необработанные записи.

Большую коллекцию не стоит возвращать целиком в запросе пользователя. `SCAN` читает порциями, но при изменениях может вернуть повторы и не является неизменным снимком. Память включает накладные расходы объектов: измеряйте `MEMORY USAGE`, а не только длину полезного текста.

## Команды и результат

```text
SET demo:counter 0
INCR demo:counter
# 1
HSET demo:user:7 name Анна city Москва
HGET demo:user:7 city
# Москва
SADD demo:tags go go sql
SCARD demo:tags
# 2
ZADD demo:rating 100 anna 120 boris
ZRANGE demo:rating 0 -1 REV WITHSCORES
# boris 120 anna 100
```

Рейтинг сортирует по score; равенства разрешаются по member, а не порядку прихода. String INCR ограничен допустимым целым форматом и диапазоном, не произвольной точностью.

Streams с consumer group:

```text
XGROUP CREATE demo:events workers 0 MKSTREAM
XADD demo:events * event_id e-1 kind paid
XREADGROUP GROUP workers w-1 COUNT 1 STREAMS demo:events >
# запомните возвращённый stream ID
XPENDING demo:events workers
XACK demo:events workers <полученный-ID>
```

`XREADGROUP` выдаёт запись и помещает её в список ожидающих подтверждения PEL. `XACK` убирает отметку ожидания, но не удаляет запись журнала. Падение после эффекта до подтверждения требует повторной выдачи и защиты от второго эффекта. Ошибка отдельной команды `MULTI/EXEC` не откатывает остальные; длительный Lua-скрипт задерживает другие команды.

## Проверь себя

1. **Удаляет ли XACK саму запись журнала?**

   <details>
   <summary>Ответ</summary>

   Нет. Он убирает ожидание подтверждения доставки; срок хранения и очистка журнала настраиваются отдельно.

   </details>

2. **Почему MULTI/EXEC не равно SQL-транзакции?**

   <details>
   <summary>Ответ</summary>

   Ошибка одной выполненной команды не откатывает остальные. Сохранность также зависит от настроек Redis.

   </details>

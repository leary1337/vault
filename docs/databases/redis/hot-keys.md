# Горячие и большие ключи

Горячий ключ получает непропорционально много обращений. Например, одно популярное объявление создаёт половину чтений сервера. Добавление узлов Cluster не делит сам ключ: у него по-прежнему один владелец.

## Сначала различить частоту и размер

Маленький ключ с миллионом чтений нагружает сеть и обработку команд. Большой список с редким чтением целиком тоже создаёт задержку. Большой ключ и горячий ключ — разные причины, хотя могут совпасть. Сопоставляйте частоты по приложению, задержки команд, размеры через `MEMORY USAGE` и состояние узлов.

## Если горячими стали чтения

Короткий локальный кэш и объединение одинаковых запросов уменьшают обращения к Redis. Копии для чтения могут распределить нагрузку, но добавляют задержку актуализации. Заранее определите, сколько устаревания допустимо. TTL со случайной добавкой уменьшает одновременное истечение копий.

## Если горячими стали записи

Счётчик можно разбить на несколько ключей и суммировать при чтении; цена — сложнее чтение и гарантия точного результата. Пакетирование уменьшает число команд, но добавляет задержку. Не переносите такой подход на операции, которым нужен немедленный единый порядок.

Большие коллекции читайте порциями, ограничивайте размер ответа и следите за сложностью команд. `SCAN` не является неизменным снимком, а `UNLINK` переносит освобождение памяти в фон, но не уменьшает размер ваших ответов.

## Диагностика с ожидаемым смыслом

```text
INFO commandstats
SLOWLOG GET 10
MEMORY USAGE demo:large
SCAN 0 MATCH demo:* COUNT 100
```

`commandstats` указывает дорогой тип команд, не конкретный виновный ключ. `SLOWLOG` измеряет исполнение, не полную передачу ответа: большой GET может быть медленным из-за сети. `MEMORY USAGE` оценивает память с накладными расходами. `SCAN` возвращает курсор и порцию; продолжайте до курсора 0 и учитывайте возможные повторы. `COUNT` — подсказка размера, не гарантия точного числа элементов.

Если ключ читают 100000 раз в секунду, локальный кэш двадцати экземпляров с TTL в секунду может резко уменьшить обращения к Redis, но допускает устаревание. Для точного счётчика записей простое копирование не подходит: нужно согласовать изменения. Разбитый счётчик даёт либо дорогой сбор частей, либо результат с задержкой.

UNLINK отделяет удаление key из пространства имён от фонового освобождения памяти; освобождение не моментальное. Перенос большого key в Cluster всё ещё стоит сети и времени. Ограничивайте размер коллекций в модели, а не только настраивайте timeout клиента.

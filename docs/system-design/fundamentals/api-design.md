# Контракт API при проектировании

API определяет смысл действия для клиента: кто вправе вызвать его, что означает успех и как повторять после потери ответа. Формат JSON — только часть этой договорённости.

## Как это работает

Для каждой операции опишите необходимые права, параметры, результат и ошибки. Отделите принятие фоновой задачи от её завершения. Укажите общий срок, предел размера и возможность безопасного повтора. Стабильный код ошибки нужен программе, понятное пояснение — человеку.

В изменяемом списке продолжение должно опираться на устойчивый порядок. Смещение OFFSET проще, но добавление строк между страницами способно вызвать повтор или пропуск. Курсор по времени и ID определяет границу; он не обязательно создаёт снимок всей выдачи.

Совместимость касается смысла: смена рублей на копейки ломает клиента даже при том же целочисленном поле. Для protobuf не переиспользуют удалённые номера полей. Подробнее: [API и условные обновления](../../backend-architecture/api-design.md).

## Разобранный пример

Для списка объявлений порядок задаётся (updated_at,id). Продолжение ищет строки после этой пары с тем же фильтром. Если курсор относится к другому фильтру, сервер отклоняет его или явно начинает новую выдачу. Один timestamp недостаточен при одинаковом времени.

Для изменения GET возвращает ETag версии 7, PATCH требует её через If-Match. Параллельная запись создала версию 8: условное изменение не выполняется, ответ — 412. Если ответ на успешное изменение потерялся, сама проверка версии не хранит прежний результат; для этого нужен отдельный ID намерения или запрос актуального состояния.

## Проверь себя

1. Почему схема полей не описывает весь контракт?
2. Равен ли курсор снимку списка?

<details>
<summary>Ответы</summary>

1. Она не задаёт права, гарантии повтора, смысл успеха и допустимую старость.
2. Нет. Новые и удалённые элементы меняют набор, если снимок не обеспечен отдельно.

</details>

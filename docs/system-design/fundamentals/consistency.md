# Согласованность при проектировании

Разным операциям нужны разные гарантии свежести. Продавец ожидает увидеть свой новый текст, а публичный поиск иногда может обновиться позже.

## Как это работает

Опишите требование через наблюдение клиента: какая завершённая запись должна быть видна следующему чтению. Если нужна своя версия, передавайте её номер и заставляйте читателя проверять применение. Если допускается задержка, задайте измеряемый срок и поведение при его нарушении.

Отдельно рассмотрите удаление, права и денежные правила: старое значение здесь способно изменить правильность. Обещание eventual consistency означает сходимость в условиях модели, а не автоматически обновление за пять секунд. Подробнее: [модели согласованности](../../distributed-systems/consistency-models.md).

## Разобранный пример

После изменения клиент получил версию 12. Карточка читается из основного узла либо копии, уже применившей версию не ниже 12. Поиск может иметь цель появления за пять секунд, но эту границу измеряют и защищают отдельно.

Закрытое объявление может остаться в старом поисковом фрагменте. Проверка карточки запрещает переход к объекту, но не удаляет текст из уже полученной выдачи. Поэтому строгий отзыв содержания требует правил для поиска и фотографий тоже.

## Проверь себя

1. Можно ли назначить одну гарантию всей системе?
2. Чем полезна версия ответа?

<summary>Ответы</summary>

1. Нужно отдельно описать операции и данные, для которых она обещается.
2. Следующий запрос может требовать как минимум состояние своей записи.

# Наблюдаемость как часть проекта

Система должна позволять отличить возможные причины отказа. Поэтому диагностические данные проектируют вместе с путём запроса, а не добавляют только после аварии.

## Как это работает

Метрики показывают масштаб и изменение, логи — отдельные события, трассировки — путь операции. На границе очереди измерьте ожидание и возраст работы; на границе БД отделите получение соединения от SQL. Для асинхронного поиска измерьте время от записи до видимости.

У каждого обещания нужен наблюдаемый показатель и оповещение, требующее действия. Данные ограничивают по объёму и очищают от секретов. Уникальные ID используют в логах и трассировках, а не в метках каждого ряда. Подробнее: [метрики](../../observability/metrics.md).

## Разобранный пример

p99 API вырос со 150 до 900 мс, p99 SQL остался 40 мс, ожидание соединения достигло 700 мс. Сначала проверяйте время владения соединениями и рост входа, а не объявляйте SQL медленным.

Метка route=/ads/{id} имеет ограниченное число значений. Метка с каждым ID объявления создаёт миллионы рядов. Среднее 50 мс не исключает p99 в две секунды. Низкая доля HTTP-ошибок тоже не доказывает свежесть поискового индекса.

## Проверь себя

1. Как отличить дорогой SQL от ожидания пула?
2. Почему ID события не хорошая метка метрики?

<details>
<summary>Ответы</summary>

1. Измерить эти два этапа отдельно.
2. Создаёт практически неограниченное число рядов; для него подходят логи и трассировки.

</details>

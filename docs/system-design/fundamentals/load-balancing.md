# Балансировка: как распределять запросы

Балансировщик направляет обращения к рабочим экземплярам сервиса. Его задача — распределить полезную нагрузку, а не просто выдать всем одинаковое число соединений.

## Как это работает

Балансировка транспортного уровня видит соединения. Одно соединение HTTP/2 может нести тысячу запросов, другое — десять, поэтому равное число соединений не гарантирует равной работы. Балансировка уровня HTTP видит отдельные запросы, но добавляет обработку протокола и границу доверия.

Проверка готовности определяет, кому давать новую работу. При остановке экземпляр сначала перестают выбирать, затем дают уже принятым запросам завершиться до конечного срока. Изменение списка не мгновенно доходит до всех клиентов и прокси.

Повтор после отказа выбирают с учётом смысла операции: балансировщик не должен незаметно повторять запись без гарантии защиты от дублей. Измеряйте стоимость запросов, задержки и состояние каждого экземпляра.

## Разобранный пример

Два HTTP/2-соединения распределены по двум экземплярам: первое несёт 1000 запросов/с, второе десять. По соединениям равновесие, по работе — стократная разница. Отдельные запросы можно распределять на уровне HTTP, учитывая занятость.

При остановке узел помечают неготовым, ждут распространения, прекращают новые приёмы и завершают текущие запросы. Таймер завершения конечен; неизвестный результат незавершённой записи всё равно выясняют по ID операции. Не доверяйте заголовку IP клиента от произвольного отправителя: прокси должен очищать и задавать его по правилу доверия.

## Проверь себя

1. Почему число соединений не равно нагрузке?
2. Что проверять при завершении экземпляра?

<details>
<summary>Ответы</summary>

1. Одно соединение может нести множество запросов с разной стоимостью.
2. Прекращение новой работы, распространение маршрутов и исход уже принятых операций.

</details>

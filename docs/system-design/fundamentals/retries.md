# Повторы как часть архитектуры

Повтор повышает шанс успеха при временной ошибке, но увеличивает нагрузку. Архитектура должна определить владельца повторов и общий срок действия.

## Как это работает

Для каждой операции опишите безопасный повтор и классы ошибок. После потерянного ответа запись может быть уже выполнена; ID намерения защищает второй эффект. Ошибка данных не исправляется ожиданием.

Общий бюджет ограничивает дополнительные попытки, в том числе у прокси и библиотек. Иногда медленное чтение запускают второй раз до завершения первого — это спекулятивный повтор. Он тоже расходует мощность, а отмена проигравшего не гарантирует мгновенного прекращения на сервере. Подробнее: [политика повторов](../../backend-patterns/retries.md).

## Разобранный пример

Сто запросов/с с тремя попытками дают до трёхсот обращений. Три вложенных слоя по три попытки дают до 2700. Бюджет дополнительных попыток в 10% требует определить базовый поток и окно подсчёта.

Спекулятивный повтор допустим для дешёвого повторяемого чтения с учётом бюджета. Для записи внешнего эффекта нужна строгая защита намерения. После подтверждённой отмены транзакции из-за известного конфликта повторяют её целиком с новым снимком; таймаут подтверждения COMMIT требует выяснить исход.

## Проверь себя

1. Когда можно заново выполнить SQL-транзакцию?
2. Чем опасен таймаут записи?

<details>
<summary>Ответы</summary>

1. После известной отмены при допустимом конфликте, целиком и с новым снимком.
2. Результат неизвестен, а повтор без ID может создать второй эффект.

</details>

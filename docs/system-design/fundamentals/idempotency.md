# Защита API от повторного эффекта

При проектировании записи заранее определите, как клиент повторяет потерянный ответ. ID намерения должен связывать попытки, но не смешивать разных пользователей и операции.

## Как это работает

Установите область ключа: арендатор, пользователь и тип действия. Сохраните значимые параметры и результат. Повтор того же действия возвращает прежний результат; тот же ключ с другими параметрами отклоняют. Сравнение нормализованных значимых полей надёжнее случайного порядка полей JSON.

Короткая локальная операция сохраняет ключ вместе с результатом одной транзакцией. Долгая внешняя работа требует состояния, восстановления и проверки неизвестного исхода. Срок хранения ключа задаёт окно гарантии. Подробнее: [реализация идемпотентности](../../backend-patterns/idempotency.md).

## Разобранный пример

Пользователь A создал объявление с ключом k17. Повтор A получает прежний ID; пользователь B не должен получить чужой ответ, даже угадав k17. Если A прислал другой текст с тем же ключом, сервер возвращает документированный конфликт параметров.

Через сутки ключ удалён. Поздний повтор теперь способен создать второе объявление. Если требуется более долгая защита, нужен устойчивый ID продукта или запрет слишком поздних повторов. Состояние «обрабатывается» без владельца и восстановления после падения может навсегда остаться занятым.

## Проверь себя

1. Зачем ключу область действия?
2. Что обещать после удаления ключа?

<details>
<summary>Ответы</summary>

1. Чтобы намерения разных пользователей и типов операций не столкнулись и не раскрыли данные.
2. Прежняя защита уже не действует, если её не обеспечивает другой механизм.

</details>
